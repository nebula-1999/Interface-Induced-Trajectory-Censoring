# P4 结果：跨家族前瞻检验（2026-09-02）

预测写于运行之前，见 `p4/PREREGISTRATION.md`（commit `3d9cf72`，
协议偏离补记 `2e5cd3c`）。以下按预测逐条对账，**包括无信息量的那一条**。

## 一、Qwen3 反事实梯子：预测成立，且是本轮最有价值的产出

模板信封 `<tool_call>` 与 hermes 一致 → 预测「解析率 > 0」。

| 臂 | 服务端解析 | **静默分数（tight，未解析）** | 真 parser 损失 | 最终通过 |
|---|---|---|---|---|
| Qwen3-0.6B | 86 | 1 | 0 | 24 |
| Qwen3-1.7B | 44 | 1 | 0 | 24 |
| Qwen3-4B | 70 | 2 | 0 | 66 |
| Qwen3-8B | 97 | 0 | 0 | 73 |
| **对照：Coder 1.5B–32B（错配）** | **恒 0** | **0→4→21→36→80** | 0 | 31–68 |

**这是 §5.2 需要的反事实对照。** 最大的混淆是「emitted 列随规模增长，可能只是
大模型更会写 JSON 的一般能力趋势」。此处：同样跨越一个数量级的规模范围，
**接口匹配时静默分数是 1/1/2/0，不增长**；接口错配时是 0→4→21→36→80，单调上升。
能力增长本身不产生 undercount，**错配才产生**。

**必须同时报的两点**：
1. 解析列**不单调**（86→44→70→97），1.7B 有一个坑。方向不影响结论（四档全部
   远大于 0），但不能写成"随规模上升"。
2. Qwen3 各臂在 `--default-chat-template-kwargs '{"enable_thinking": false}'` 下
   服务。不关思考会把 2048 token 全用在 `<think>` 上、`finish=length`，那是与
   信封无关的混淆（协议偏离已于跑批前记录）。

## 二、Granite 臂对：预测形式上命中，但**无信息量**，不计入支持

| 臂 | 解析 | 含 `<\|tool_call\|>` | 裸 JSON 调用 | 最终通过 |
|---|---|---|---|---|
| Granite-3.1-8B + hermes | 0 | 0 | 0 | 48 |
| Granite-3.1-8B + **granite**（rescue） | **0** | 0 | 0 | 48 |

两条臂的 vLLM 启动参数已核对确为 `hermes` 与 `granite`，非配置错误；温度 0 下
两条轨迹逐字节相同，因为解析器不同但都无物可解析。

**判读**：Granite-3.1-8B 在本任务上**根本不发起工具调用**——既没有它自己的
`<|tool_call|>` 信封，也没有裸 JSON 调用；73 次"提及 run_tests"全部是散文与代码
围栏里的字符串。它直接作答并解出 48/100。

按预注册写死的标准：

> rescue 臂是必需的，不是加分项。只跑 hermes 得到 0，无法排除"模型压根没调工具"。

**rescue 给出 0，因此这条臂无法检验信封假设，记为无信息量，不作为支持证据。**
预测「Granite+hermes ≈ 0」在形式上未被推翻，但推翻它的机会从未出现。

## 三、对 P2「第二个家族的 scale ladder」的结论

原意义上的 P2 要的是**第二条 undercount 梯子**。本轮**没有得到**，而且现在有了
更具体的理由：

- 零算力普查的九个家族里，六个默认模板不注入 tools（不适合检验 envelope 层）；
- 剩下三个中，Granite 在本任务上不调工具（本轮实测），GLM-4-9B 在 vLLM 0.27.1
  下无适配 parser 因而做不出 rescue 对照（本轮未跑）；
- Qwen3 有完整梯子但**信封与 hermes 一致**，因此只能充当反事实对照。

**结论**：在现有开源模型里，找到一个「既有完整尺寸梯子、又与 hermes 信封错配、
且在该任务上确实会发起工具调用」的家族，目前未能做到。这既是局限，也提示
Qwen2.5-Coder 那种错配的具体条件并不常见——但**不足以支持"错配普遍"这类主张**
（预注册 v2 已删除该说法，理由是未普查各家推荐 parser）。
