## 一、怎么讲

### 故事线和以前不一样了

以前的讲法停在「我发现接口吃掉了工具调用」。现在多了 P3，故事有了一个更好的结尾：

1. **起点**：自己训练曲线里的矛盾——最终通过率涨了，多轮修复没动
2. **发现**：工具调用要经过模板、parser、执行器；对不上时 HTTP 200 + 空 `tool_calls`
3. **外部证据**：BFCL 2×2、τ-bench——不是我自己 harness 的问题
4. **机制**：不是 parser 有 bug，是模型、模板、parser 三方契约对不上
5. **转折**：我设计了一个可能推翻自己的实验——训练里只修 parser。工具执行 10 → 16,844，**多轮修复没涨**
6. **收窄**：接口决定训练里能采到什么经验；经验恢复了，学习收益不会自动出现

**第 5 步是全场最值钱的一段。** 它说明你会主动去证伪自己的解释，拿到负结果后会收窄结论，而不是硬撑。

### 30 秒版

> 我做了一个用 GRPO 训练的代码智能体，模型可以调用 run_tests 根据测试结果改代码。训练后最终通过率涨了，但靠第二轮修好的题一直没变。我追下去发现工具调用经常根本没被执行：模型输出的格式和服务端解析器期望的对不上，服务端照样返回 200，只是调用列表为空。在 BFCL 上，同一个模型只改服务端配置，官方分数从 0.00 到 0.96。我又在训练里只修解析器做了单变量对照，工具执行从 10 次变成一万六千多次，但多轮修复能力没有提升。所以结论是：接口决定模型能获得什么经验，但修好接口不等于学会用反馈。

### 2 分钟版

> 我最初做的是一个用 GRPO 训练的代码智能体，模型写完代码可以调用 run_tests 看结果再改。训练 150 步后最终通过率涨了，但拆开看几乎全是首轮变好，靠后续轮次修好的题一直是 540 道里五到十道。我去查工具到底有没有被调用，发现问题在接口：模型输出要经过 chat template、parser、执行器才变成动作，只要格式对不上，服务端照样返回 200，只是调用列表为空，看起来就像模型不想调工具。
>
> 为了确认不是我自己 harness 的问题，我在 BFCL v4 上用它官方的数据、执行器和评分器复现：同一个模型，只改服务端适配器配置，simple_python 从 0.00 到 0.96。再做模板和 parser 的 2×2：从文档配置出发，单换哪一个都恢复不了，两个一起换，首请求 196/200 被解析——问题出在两者的配对上。τ-bench 上被执行的调用也是 0 对 636。我还重放了 vLLM 自己的解析逻辑，确认 parser 是按规范在工作，坏的是模型、模板、parser 三方之间的契约。
>
> 然后我做了一个可能推翻自己的实验：在 verl 的真实训练里，两条 7B 臂只差 parser 注册这一处。修好后工具执行从 10 次变成 16,844 次，但两套 held-out 评测下多轮修复都没有提升。所以最后的结论比我一开始想的窄：接口决定了训练里能采到什么经验，但经验恢复不等于学会利用反馈。

### 5 分钟版的节奏

| 时间 | 讲什么 | 注意 |
|---|---|---|
| 0:00–0:40 | 训练曲线的矛盾 | 讲完**停一下**，让对方意识到这是个真问题 |
| 0:40–1:30 | 排查：日志里那个"调用次数"其实是耗时；自己插桩 | 说清为什么不能插在沙箱入口 |
| 1:30–2:30 | BFCL 2×2、τ-bench | 2×2 四格报出来，**不要说"主效应为零"** |
| 2:30–3:15 | 机制：不是 parser bug；四个家族；Llama 的 strict | Llama 讲"三个对照都错了" |
| 3:15–4:20 | **P3**：单变量、10 → 16,844、多轮修复不动 | 全场最重要的一段 |
| 4:20–5:00 | 结论边界 + 做法上的收获 | **主动**说局限 |

### 四条原则

1. **从别人的尺子开始。** 先讲 BFCL，再讲自建探针。对方第一个疑问一定是"会不会是你 harness 的问题"。
2. **每个数字带分母。** "5 到 10 道，540 道里"，不是"很少"。
3. **结论说到哪里为止，自己先说。** 别等对方问。
4. **被追问时先说能证明什么，再说不能证明什么。** 两半都说，对方就挑不出你夸大。

## 二、30 个问题

### A. 定位与贡献

**Q1. 用两分钟介绍一下这个项目。**
用上面的 2 分钟版。

**Q2. 你是怎么发现这个问题的？**
> 从自己训练曲线里的矛盾。1.5B、150 步 GRPO，三个独立 run 的 pass@1 都涨了 2.6–2.8 分——单个都不显著，我靠的是三次方向一致。但新通过的题 91–94% 是第一轮就过的，靠第二轮以后修好的题在 540 道里一直是 5 到 10 道。如果是模型太小学不会多轮，工具调用数应该是个小数，不应该是零。我去查日志，发现 verl 里那个看起来像调用次数的指标其实是耗时，就在 agent 侧两个调用点自己插了计数——不能插在沙箱入口，因为 reward 函数评分也走那里，会把评分混进调用数。插完发现 FC 臂工具执行是 0。
>
> 补一句边界：1.5B 那个零是"过度决定"的——那个模型在训练提示词下本来就不发出点名正确的调用。它是起点，不是证据。真正的机制证据在 7B。

**Q3. 这不就是一个配置错误吗？vLLM issue 里早就有人报过。贡献在哪？**
> 具体问题确实是配置不匹配，vLLM issue #32926 报过，论文里写明了。我的贡献不是发现它，而是测量它的后果：一，在 BFCL 和 τ-bench 两个标准基准上量化它对分数的影响；二，用 template×parser 的 2×2 把组件关系拆开；三，用固定原文重放证明原始输出里确实有可恢复的调用；四，把它带进真实的 verl 训练，测它改变了多少训练经验，以及修好之后学习有没有变化。
>
> 一句话：不是发现了一个 bug，是测量了一类测量误差的后果。

**Q4. 核心发现用一句话说？**
> 观察到的工具调用率不只是模型的属性，是模型和接口这个组合的属性。同一份权重，换个服务端配置，BFCL 分数能从 0 到 0.96。第二句同样重要：在我们的设置里，把训练接口修好、经验恢复，并没有带来可检测的学习收益。

**Q5. 这个问题对谁重要？有什么实际用处？**
> 两类人。做评测的：很多工具使用 benchmark 直接报服务端解析出的调用，接口没配对，测到的是配置不是模型。做 agentic RL 的：工具分支在接口层被丢掉，策略梯度里就没有这条分支的样本，reward 曲线照样会涨。
>
> 实际产出有两个。一是建议评测至少分层报告：服务端解析数、发出但没被解析的、请求错误、确切的服务配置。二是一个 98 行的 preflight 脚本，发一个标准请求，检查返回的工具名和参数，再用 `tool_choice: required` 做阳性对照，几秒跑完。我们还查了九个家族的模型卡，能访问的八张里没有一张提到该用哪个 tool-call parser——指引在模型方和服务方两边都缺位。

### B. 机制

**Q6. 具体是怎么失败的？为什么还返回 200？**
> 以 Qwen2.5-Coder 为例。vLLM 的 hermes parser 只认被 `<tool_call>…</tool_call>` 包起来的 JSON。Coder 没在这种格式上训练过，会把调用写成裸 JSON，或者放进 ` ```json ` 代码块。hermes 看不到包装层，就当普通文本，`tool_calls` 返回空数组。请求本身没出错，所以是 200。从外面看，和"模型决定不调用工具"一模一样。

**Q7. 那是不是 parser 有 bug？**
> 不是。我逐行复刻了 vLLM 0.27.1 的 hermes 抽取逻辑，在存档的首轮输出上重放，找"按 parser 自己的规则本该接受、服务端却没接受"的情况，一例都没有。parser 是按规范在工作。坏的是三方契约：模型被训练去发什么、chat template 告诉它发什么、parser 被定义去接受什么，三者是分开配置的。
>
> 要补一句：这是"首次失败"分类。没有包装层的输出在第一步就被归类了，不会再检查 JSON 合不合法。所以"parser 漏收为零"真正被检验到的，是那些带了包装层的输出。

**Q8. BFCL 的 2×2 怎么读？**
> 四格是首请求被解析数：hermes + 文档模板 0/200，hermes + 专用模板 0/200，专用 parser + 文档模板 0/200，两个都换 196/200。从文档配置这个基线出发，单独换任何一个组件，恢复都是零，必须成对替换。两个组件是强互补的。
>
> 措辞上我要特意说清：这**不是**"两个主效应为零"。按标准因子分解，每个组件对另一个取平均的主效应是 98，为零的是基线处的**简单效应**。我早期版本写错过，后来改了。另外 2×2 比的是解析数；官方 BFCL 分数只算了两个对角配置，没有算四格。

**Q9. BFCL 从 0 到 0.96，能全算成"parser 把能力藏起来了"吗？**
> 不能。主干预同时换了 parser 和模板，模板会改变模型输入，也就改变了生成。所以 0 到 0.96 里有一部分可能是模型被新模板引导、写得不一样了。为了把这部分剥开，我们做了固定原文重放：拿原来那 100 条 simple_python 的原始输出，一个字节不改，用一个不看答案的宽松 JSON 抽取器重新解析，能重建 97 个结构合规的调用，其中 92 个通过官方 AST 评分器。说明原始输出里确实已经有可评分的调用，但不能把全部增益归给 parser。

**Q10. 四个模型家族分别怎么失败？**
> 四层。DeepSeek-Coder 在模板层：chat template 根本不注入工具。Qwen2.5-Coder 在包装层：写的是裸 JSON，不是 hermes 格式。Llama-3.1-8B 在 schema 层：会把题目要它实现的那个函数当成工具去调用。Mistral 在 token 层：重复输出 `[TOOL_CALLS]` 标记导致 400。只有 Mistral 会报错，其他三个都是静默失败。
>
> 边界：证据是不对称的。Qwen 有规模梯子和修复，Llama 有单变量干预，Mistral 连一个合格的对比都没有，DeepSeek 只是模板检查。这是四个实例，不是失败空间的完整划分。

**Q11. Llama 那个 strict:true 是怎么回事？**
> Llama 在 FC 下大约四分之一的情况会去调用"题目要它写的那个函数"，参数还是那个函数自己的参数。我先做了三个单变量对照：写更详细的 schema 说明、加思维链脚手架、换官方 chat template。三个都没降下来，思维链甚至把它从 23 升到 59——让它先分析函数签名，它就把刚分析的参数传了进去。我当时据此判断是模型缺陷。
>
> 第四个对照来自 vLLM 文档里的一句话：auto 模式下要让 schema 约束生效，工具要带 `strict: true`。加上之后，以官方模板为基线，22 条错误调用全部消失，最终通过从 44 升到 61，这个对比在多重校正后仍然显著。
>
> 它和 Qwen 不是一类：strict 是生成时的约束，改变了模型写出来的东西，属于"抑制"，不是"遮蔽"。意义在于：三个对照都"排除了替代解释"，但排除替代解释不等于找到原因。

### C. 测量与统计

**Q12. 规模梯子上那个 80/100 怎么来的？可信吗？**
> 是一个启发式分类器："tight"档要求出现命名为 run_tests 的 JSON 对象，code 字段是含 Python 的字符串字面量。它不验证 JSON 语法，也不验证代码能不能跑，所以我说"80 个 tight 分类阳性"，不说"80 个合法调用"。
>
> 校准做了两层：两名盲标注者在看到相同字节的 62 条上 κ = 0.967；分类器对第三方裁决的金标准 κ = 0.871，tight 档精度 36/40 = 0.900。如果这个精度能跨尺寸迁移，80 大约对应 72——但那只是敏感性估计。存储有 4000 字符上限会漏检，精度说明有误检，净偏差方向不可识别。

**Q13. 规模越大低估越多——会不会只是大模型更会写 JSON？**
> 这正是最大的混淆。服务端那列一直是 0，所以增长全来自"发出"那列，而大模型本来就更会写规整 JSON。为此我们事先在仓库里提交了预测，再跑一个接口匹配的 Qwen3 梯子：它的模板要求 `<tool_call>` 包装，正好是 hermes 认的。0.6B 到 8B 的静默数是 1、1、2、0，而错配的 Coder 梯子是 0 → 80。
>
> 边界：Qwen3 同时换了家族和包装层，所以它是支持性证据，不是严格反事实。它排除了"能力增长本身就足以造成低估"，但不能把原因单独归到包装层。它的解析数也不单调（86、44、70、97），而且是关掉 thinking 模式跑的——开着会把 token 预算耗在思考里，这个偏差在跑之前就记录了。

**Q14. 为什么还要做 Qwen2.5-Instruct 那条梯子？**
> 换家族回答不了"是规模问题，还是 Coder 这一支碰巧不行"——其他家族要么解析正常、要么报错、要么不注入模板，根本不会出现这种低估。Instruct 和 Coder 共用同一个 chat template，Coder 的模板就是从 Instruct 继承来的（这也是为什么"检查模板里有没有工具"会给 Coder 假阳性）。区别在于 Instruct 训练过工具调用格式。同样配置下 Instruct 的解析数随尺寸是 1、11、63、77、88，Coder 一直是 0。这把问题定位到"这个 checkpoint 有没有被训练过这种格式"。
>
> 边界：两者的整个后训练配方都不同，不能说就是格式训练这一个因素。

**Q15. 样本量够吗？100 题，还不是随机抽的？**
> 不够，局限里写在最前面。主实验 50 个满 100 题的对照臂用的是同一个题集——去污染后的前 100，不是随机抽的——所以臂与臂之间是严格配对比较。为了检查能不能推广，我们在随机 300 题上复现了梯子：服务端解析在 1500 题上仍然全是 0，tight 数是 0、4、30、40、81。7B 那一档从 21 变成 30，说明原来的子集低估了中间档——方向和单调性没变，但单个 100 题子集对中间档不是稳定估计。

**Q16. 做了多少个统计检验？多重比较怎么处理？**
> 回顾性的检验族一共 27 个，Bonferroni 阈值约 0.05/27 ≈ 0.00185。扛过校正的只有最强的干预，比如 Llama 在官方模板基线上加 strict 的最终通过提升。没扛过的只当描述性结果：Llama 的"接口修复 +12、协议 +19"两段拆分（p = 0.0075 和 0.0019），Qwen 修复后的通过率提升（n = 100 时 p = 0.093；随机 300 题复现名义 p = 0.0385）。后来加的九个原生 FC 对比单独标为探索性。
>
> 另外，p > 0.05 我不读成"没有效应"，报区间。

**Q17. τ-bench 的结果说明了什么，没说明什么？**
> 说明了这个机制能延伸到非代码、有状态、有模拟用户的环境。115 道 retail 题两臂配对，只换服务端适配器：被解析并执行的调用 0 对 636，至少执行过一次工具的题 0 对 103。文档配置那一臂的 1,389 个请求都带了 tools，789 个 assistant 轮里有调用形状的内容但没被解析，重放显示全卡在缺包装层这一步。
>
> 没说明的：任务成功率差异，7 对 10，p = 0.25，我不主张。用户模拟器是本地 Llama-3.1-8B 不是 gpt-4o，绝对分数不能和排行榜比。也不能用它判断载荷格式有没有问题——那 789 条根本没走到载荷检查那一步。规模和 RL 的结论仍然只在代码任务上。

**Q18. 什么是预注册？你为什么做？**
> 跑实验之前，把要检验的预测和判据写下来提交进 git，带时间戳。比如 Qwen3 梯子，事先写了"每个尺寸解析数都大于 0"。P3 我们在出结果前提交过一次判据修正：原来的判据会用训练里的平均奖励判断"多轮学习是否恢复"，而平均奖励恰好可以只靠首轮变好就上涨，这正是论文开头批评的那种混淆，所以改成 held-out 上的多轮救回数。
>
> 为什么做：这种研究最大的风险，是看到结果再挑支持结论的指标。预注册让"我事先打算怎么判"可以被核查。

### D. RL 与 P3

**Q19. 接口错配对 RL 训练具体有什么影响？**
> 工具调用在 parser 这一层被丢掉，采样到的轨迹里就没有工具交互，这条分支的回报样本是零；而 reward 允许直接作答拿分，直接作答一直被强化。策略梯度里没有信号把模型推向工具使用，它也没法靠探索撞到——每次尝试都在协议层被丢了。我说的是"在观察到的采样分布下，这条分支得不到直接的 on-policy 梯度"，不是数学上不可达：观察到 0 不等于概率为 0。
>
> P3 的 broken 臂里，150 步内有 8,689 次生成被分类为完整调用，被 parser 接受的只有 10 次。

**Q20. 为什么不能直接看训练的 reward 曲线来判断？**
> 因为聚合奖励可以完全由首轮变好推动。我们历史上那三条 run 就是例子：pass@1 涨了，91–94% 的新增通过是第一轮就过的，多轮修复没变。用"reward 涨了"判断多轮学习恢复，会把首轮改进错当成多轮能力。所以 P3 改用 held-out 上的多轮救回数作判据——"最终过、且首轮没过"的题数——并且在出结果前把这个改动提交进仓库。

**Q21. 1.5B 和 7B 为什么分开报？**
> 因为 1.5B 的零是过度决定的。在训练用的强制提示词下，那个 1.5B 根本不发出点名 run_tests 的调用——它会去调用题目要写的那个函数。没有合格的调用可以被丢掉，修 parser 也救不了，这种零不能归因给接口。会发出合格调用的是 7B，所以接口归因和 P3 对照都在 7B 上做。尺度依赖本身就是结果。

**Q22. P3 是怎么设计的？**
> 两条 7B LoRA 训练臂，各 150 步。模型、数据、种子、LoRA 配置、奖励函数、验证器全部一致，唯一区别是 verl 里 `multi_turn.format` 选哪个 parser：broken 用 hermes，repaired 用一个接受 Qwen2.5-Coder 实际输出格式的自定义 parser。关键点是 verl 的 AgentLoop 有自己的 parser 注册表，给 vLLM 装插件改不了训练。评测在训练里就地进行，每 30 步一次，在 542 道 held-out 题（HumanEval+ 164 + MBPP+ 378）上算多轮救回数。
>
> 用 LoRA 是因为 7B 全参 RL 在单张 80GB 卡上会在 actor 更新阶段 OOM。两条臂配置相同，臂间比较不受影响；但和历史上 1.5B 全参的 run 不严格可比。

**Q23. 你怎么保证训练里那些计数是对的？**
> 三点。一，计数插在 agent 侧的调用点，不插沙箱入口，因为 reward 函数评分也调用沙箱。二，钩子要装进 verl 的 Ray worker 进程，直接 import 装不上，我们用 sitecustomize 在进程启动时注入；而且是自证式的——任何一个钩子触发次数为零，整次实验判无效，而不是安静跑完。我们早期真踩过"钩子没装上、脚本却成功退出"。三，保留每次生成的原文和 sha256，事后能复算，broken 臂 19,203 条全部校验通过。
>
> 顺带：repaired 臂 16,912 和 16,844 不矛盾。前者是被 parser 接受的调用数，后者是生成事件数，也就是实际执行并返回 observation 的次数——有 40 次生成里含多个调用，只派发第一个，多出的 68 个没执行。

**Q24. P3 的结果是什么？**
> 接口修好了：被接受的调用 10 对 16,912，实际执行并返回 observation 10 对 16,844。
>
> 学习收益没出来：在共享的程序反馈评测里，两臂的多轮救回从第 0 步到第 150 步都是 12/542；最终通过 broken 430 → 430，repaired 430 → 427，差异不显著，我不解读为有害。后来我们又把 base、broken、repaired 三个权重放到同一个能用的原生 FC 接口下重测：base 239/542，broken 和 repaired 都是 248/542，两边各有 16 道此得彼失，p = 1，差值的保守 95% 区间是 ±3.47 个百分点。

**Q25. 为什么修好接口没带来提升？是不是你最初的假设错了？**
> 最初的解释是"多轮没学会，是因为工具从来没被执行"。P3 说明这只对了一半：接口是必要条件——没有它连经验都没有——但在我们的设置里不是充分条件。经验恢复了 1,600 多倍，多轮能力没变。
>
> 原因我们没有隔离出来。候选有：预算太短，150 步、单 seed；奖励只看最终通过比例，不告诉模型哪一轮反馈有用，首轮变好比学会用反馈更容易被强化；训练时反馈是 tool 角色的消息，共享评测里是 user 消息，存在格式迁移。这些都是假设，不是结论。
>
> 我觉得这是这个项目最有价值的部分：我设计了一个可能推翻自己解释的实验，它推翻了一半，我把结论收窄了。

**Q26. 奖励或验证器有没有被 hack 的可能？**
> 我们审计过。奖励只看最终代码的测试通过比例。三种常见作弊路径从构造上堵住了：一个测试都没跑记 0、超时记 0、没有测试字符串的题记 0。历史验证器有两个漏洞：pytest 汇总正则没锚定，程序自己打印一行像"N passed"的字可能被误读；skipped 和 xfail 没计入分母。我们在历史日志里查了这几种模式，出现次数都是 0，reward 曲线也没有出现漏洞被发现时那种台阶式跳变。P3 的两条正式臂用的是修好的验证器，并保留完整 rollout，这个缺陷影响不到 P3。另外，报告的通过率走的是另一条更严格的路径，不经过这个正则。

### E. 局限与下一步

**Q27. 这个工作最大的局限是什么？**
> 第一，P3 是单 seed、单个预算，只能说"在这个规模、预算和 seed 下没检测到收益"，不能说更长训练或别的算法也不会有。第二，规模梯子和 RL 结论都只在一个代码任务上；外部基准证明的是机制能延伸，不是规模趋势能延伸。第三，第二个家族的错配规模梯子没拿到——普查了九个家族，六个不注入 OpenAI 式工具，Granite 试了，它在两种 parser 下都不调用，判为无信息量。第四，所有测量都绑定 vLLM 0.27.1 和 verl 0.9.0。

**Q28. 如果重做，或者接下来做，你会怎么做？**
> 重做的话：从第一天就逐层记录——发出、解析、执行、返回、最终分数，以及当时生效的 parser 和模板版本。我们早期没记 parser 名，后来只能从实验臂名字推断。评测从一开始就跑在训练里。P3 至少三个 seed。任何 FC 实验之前先跑 preflight。
>
> 接下来：把奖励和信用分配当成独立因素研究——保持任务、接口和预算可比，加轮级信号，同时看最终通过、在固定错误初稿上的修复成功率、调用成本。不会按调用次数给奖励，那会鼓励重复测试刷分；要奖励的是有效调用，不是调用本身。

### F. 你本人

**Q29. 这个项目里你犯过什么错？怎么发现的？**
> 印象最深的四个。
> 一，Llama 那件事：三个单变量对照都指向模型缺陷，我写进了报告，第四个对照推翻了它。
> 二，人工标注第一轮 κ 只有 0.713，我差点以为标注者不可靠。后来发现标注包把每条输出截在 2400 字符，那些调用恰好在截断之后——标注者看到的副本里根本没有调用，12 条分歧里 11 条是这种。这和论文主题是同一个机制：一个截断的工具让证据消失，结论变成"模型没调用"。
> 三，早期在一个含请求错误的实验臂上算过一个 p = 0.648。后来定了规则：含请求错误的臂不算 p 值，用代码强制执行，那个数撤回了。
> 四，统计措辞：我早期把 BFCL 2×2 写成"两个主效应为零"，其实主效应是 98，为零的是基线处的简单效应。
>
> 怎么发现的：靠两个习惯——每个数字回到原始文件复算；判据先写下来，再看结果。

**Q30. 你用了多少 AI 辅助？哪些是你自己做的？**
> 用了很多，论文里有专门的 AI 使用声明：实验设计反馈、实现和调试、结果解读、文献检索、写作和修改都有 AI 参与。我负责的是：提出和界定问题、决定做哪些对照、判断结论能说到哪里、核对——每个报告的数字都回到持久化的原始文件核过。这个项目里最容易出错的不是写代码，而是判断"这个零到底说明了什么"，这部分必须自己负责。

> ⚠️ **这一题必须按真实情况答，不要照背。** 你说哪部分是自己判断的，面试官就会挑那部分深挖。下面那一节就是为这个准备的。

## 三、被深挖时，你必须能脱稿讲清楚的十件事

面试官判断"是不是你做的"，不靠你讲得多流畅，靠追问细节时你能不能接住。这十件事要能不看文档讲出来：

1. **hermes 的解析规则**：正则匹配 `<tool_call>(.*?)</tool_call>`，捕获内容交给 `json.loads`，要求有 `name` 和 `arguments`。没有标签就不解析。
2. **verl 的 parser 和 vLLM 的 parser 不是一个东西**：AgentLoop 有自己的 ToolParser 注册表，由 `multi_turn.format` 选择；给 vLLM 装插件改不了训练。
3. **为什么计数不能插在沙箱入口**：reward 函数评分也调沙箱。
4. **GRPO 怎么算优势**：组内候选的奖励相对组均值（和标准差）归一化；一组全是 0 分时组内没有差异，就没有有效梯度信号。
5. **"救回"的定义和分母**：最终通过且首轮没过；分母 542 = HumanEval+ 164 + MBPP+ 378。
6. **主效应 vs 简单效应**：四格 0/0/0/196，主效应各 98，基线处单换的简单效应为 0。
7. **tight 分类器是什么、不验证什么**：命名 run_tests + code 是含 Python 的字符串字面量；不验证 JSON 语法和可执行性。
8. **16,912 vs 16,844**：调用数 vs 生成事件数；一次生成多个调用只派发第一个。
9. **1.5B 的零为什么是过度决定的**：它根本不发出点名正确的调用。
10. **0.00185 怎么来的**：27 个检验的 Bonferroni，0.05/27。

## 五、面试前要处理的三件事

**1. 检查你的简历。** 如果写了"两个主效应精确为零""6–9/540""8,591/7"，现在就改。简历是面试官唯一一定会看的东西。参考写法：

> **工具调用接口对智能体评测与 RL 训练的系统性干扰**
> *Interface-Induced Trajectory Censoring*, arXiv:2609.03966
> - 训 1.5B 代码智能体时，pass@1 涨了 2.8 分，靠第二轮以后救回的题 150 步内一直是 5–10/540。逐层插桩后定位到工具调用在接口层被丢弃：模型写出调用形状的输出，但不在 parser 认的格式里，HTTP 200、`tool_calls` 为空、全链路不报错。
> - 50 个满 100 题、共用同一题集的对照臂，覆盖 4 个模型家族、1.5B–32B 五个尺寸；三条规模梯子分别检查三个混淆（Coder 错配下 0 → 80/100、Instruct 同血统对照、预注册的 Qwen3 匹配接口梯子）。

> - 设计单变量 RL 对照：两条 7B LoRA 训练臂只差 verl parser 注册，工具执行 10 → 16,844 次，两套 held-out 评测均未检测到多轮修复提升（原生 FC 下 248 对 248，p = 1），据此把结论收窄为"接口决定经验，不保证学习"。
