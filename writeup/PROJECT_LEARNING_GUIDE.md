## 1. 先用你的算法背景理解 Agent

### 1.1 从一次预测，变成一个反馈循环

你熟悉的监督学习可以简化为：输入样本 `x`，模型产生预测 `fθ(x)`，与标签比较，得到损失。

普通代码生成类似：给模型题目，它生成一份程序，结束。程序是否正确，之后由评测器判断。

工具型 Agent 多了一条环境反馈路径：模型生成程序，申请运行测试，系统执行测试，把错误信息交回模型，模型据此修改程序。它可能重复几轮，也可能直接回答而不调用工具。

```text
题目 → 模型生成初稿 → 请求运行测试 → 执行器运行测试
                         ↑                  ↓
                      修改代码 ← 模型读取真实测试反馈
                                           ↓
                                     提交最终答案
```

这里的“Agent”不必意味着很多模型，也不必意味着复杂的规划器。一个模型、一个工具和一个循环，就可以构成我们研究的工具型 Agent。

从控制论的角度理解很有帮助：模型提出控制动作，系统把动作送到环境，环境返回观测。一个控制器即使输出了正确的控制意图，如果通信协议让执行器读不到它，闭环仍然无法工作。

### 1.2 四个常被混用的东西

| 名称 | 在本项目中的含义 | 不能直接等同于 |
|---|---|---|
| 模型 model | 权重、架构、tokenizer 所定义的文本生成器 | 整个 Agent 系统 |
| 策略 policy | 给定当前历史，生成下一段输出的分布 | 固定的 Python 工作流 |
| Agent | 策略加上交互循环、工具接口、停止规则等 | 单独一套权重 |
| 工作流 workflow | 由程序预先安排的调用和分支 | 模型自主决定采取了这些动作 |

两者可以组合：工作流负责预算和权限，模型决定下一步做什么。不要用“是否有 while 循环”来判断是否具有自主工具使用能力，要看**谁决定调用工具，谁提供反馈**。

### 1.3 推理、上下文变化、训练，是三种不同的变化

同一个 Agent 连续改三次代码，通常只是推理期间增加了上下文，权重没有更新。

```text
读报错后修改代码：历史 h 变了，θ 不变。
RL 训练后再做题：θ 变了，策略 πθ 发生改变。
换 parser 后执行恢复：接口 I 变了，θ 可能完全没变。
```

这三个过程都可能让最终成功率提高。因此，“它最后修好了”本身不能说明“它通过 RL 学会了修复”。

### 1.4 Agent 常见能力在这里分别是什么

- **规划**：判断先写代码、先检查边界条件，还是先执行测试。我们的项目没有单独训练一个规划模块。
- **工具选择**：在提供的工具中选择合法工具。本项目代码任务主要只有 `run_tests`，仍会出现选错名字的问题。
- **参数构造**：把完整 Python 程序放进工具的 `code` 字段。
- **反馈利用**：根据真实报错做有针对性的修改，而非仅仅再生成一次。
- **记忆**：最基本的是消息历史。我们没有证明外部长期记忆或检索系统带来了收益。
- **停止**：何时提交最终答案，何时达到最大轮次或 token 限制。

RAG 是检索相关资料后辅助生成；它可以成为 Agent 的工具。MCP 是工具和资源接入的一种协议；它不等于工具选择策略。多智能体是多个角色或模型协作。上述东西都不是我们当前核心实验的必要组成，不要为了显得全面而把它们写成已经研究过。

**本章自测：**模型看报错改对了代码，但没有更新参数，你会说它“训练出了新能力”吗？不会；你观察到的是这个 checkpoint 在该反馈条件下能够修复。

### 1.5 Token、上下文和解码预算

语言模型逐步预测下一个 token 的分布。token 不一定是一整个单词：一个函数名、中文词或特殊标记可能由一个或多个 token 表示。模型持续生成 token，直到遇到停止条件或预算耗尽。

你可以把下一步写成 `p(next_token | 题目、工具说明、已有输出、历史反馈)`。工具说明和错误日志都通过这个条件分布影响下一步；它们不是脱离模型输入的神秘控制模块。

| 参数／概念 | 影响什么 | 本项目中的典型风险 |
|---|---|---|
| temperature | 采样分布的尖锐程度 | 不同温度改变调用倾向和代码多样性 |
| top-p | 采样时保留的候选概率质量范围 | 它与 temperature 一起定义解码条件 |
| max tokens | 单次或整段响应的生成预算，具体含义依接口 | 调用还没闭合就被截断 |
| context window | 模型一次能处理的上下文容量 | 多轮报错和工具输出积累后超限 |
| stop token／stop string | 何时结束生成 | 可能在调用或代码尚未完整时结束 |

温度为零通常表示采用贪心式选择，但不应把它当成跨硬件、并发和所有实现都保证逐字可复现的承诺。

还要区分两个截断：模型达到输出预算而停止生成；日志系统把已经生成的长文本只保存前 4000 字符。前者改变模型产生的结果，后者破坏我们事后的观测。修复日志长度不能补回第一次没有生成出来的尾部。

### 1.6 从 MDP 到语言 Agent 的历史状态

如果你熟悉强化学习中的状态、动作、奖励，可以这样对应：题目与历史对话构成策略可见信息，调用工具是环境动作，工具返回是 observation，最终测试给 reward。

但模型通常看不到环境完整状态。例如 τ-bench 中它需要调用 API 才知道订单信息，因此更接近部分可观测情形。用历史 `h_t` 而不是假设模型看到了完整 `s_t`，往往更准确。

一条 episode 从题目／用户任务开始，到提交最终答案、任务终止或预算耗尽结束。工具动作后的新 observation 会改变未来历史，因而早期一次解析失败可能改变整条后续轨迹。

这就是“轨迹被改变”比“少记了一个计数”更重要的地方：如果执行没有发生，之后的报错、修复和成功路径也可能根本没有被采样出来。

## 2. 一次工具调用究竟发生了什么

### 2.1 用一道简单题走完整个过程

教学题目：实现 `add(a, b)`，返回两个参数的和。

模型可用工具的声明可以长这样：

```json
{
  "type": "function",
  "function": {
    "name": "run_tests",
    "description": "Run the submitted Python program against this task's tests.",
    "parameters": {
      "type": "object",
      "properties": {"code": {"type": "string"}},
      "required": ["code"],
      "additionalProperties": false
    }
  }
}
```

`name` 是系统中已注册的工具名，`description` 告诉模型它做什么，`parameters` 约束调用参数的结构。这里的 JSON Schema 只说明 `code` 必须是字符串，**并不证明字符串中的 Python 程序正确**。

注意题目函数与工具函数的区别：

```text
add(a, b)       题目要求模型实现的程序功能
run_tests(code) 系统允许模型调用的外部工具
```

模型如果输出 `add(a=1, b=2)`，它在调用题目函数，并没有提交 `add` 的实现去测试。这正是 Llama 实验中需要检查的错误类型。

### 2.2 模型本身输出的是 token

对语言模型而言，工具调用通常仍是一串 token。模型可能生成：

```text
<tool_call>{"name":"run_tests","arguments":{"code":"def add(a, b):\n    return a + b"}}</tool_call>
```

它没有亲自启动 Python。外部程序首先把这串文本识别为调用，然后才可能执行。

同一个调用也可能被写成：

```json
{"name":"run_tests","arguments":{"code":"def add(a, b):\n    return a + b"}}
```

人的理解几乎一样；但如果解析规则必须先找到 `<tool_call>`，第二种写法就不会成为结构化调用。

### 2.3 消息格式与模型原文不是同一层

服务端成功解析后，API 可能返回下面这种结构；这是教学示例，具体字段以实际服务版本为准：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_001",
      "type": "function",
      "function": {
        "name": "run_tests",
        "arguments": "{\"code\":\"def add(a, b):\\n    return a + b\"}"
      }
    }
  ]
}
```

外层 JSON 中，`arguments` 在这类接口里常常还是一段 JSON 字符串，需要再解码一次。这也是为什么日志中会出现很多反斜杠。不能只看“外层响应是合法 JSON”，就判断内部工具参数合法。

如果服务端没识别调用，可能返回普通 `content`，而 `tool_calls` 缺失或为空。两种响应都可能是 HTTP 200。

HTTP 200 说明请求在 HTTP/API 层被处理了；它不保证模型调用了正确工具，更不保证任务完成。

### 2.4 谁真正执行代码

Agent 的宿主程序做工具名检查、参数检查和工具分发，然后执行 `run_tests`。测试结果可能是：

```text
1 failed, 4 passed
AssertionError: expected 5, got -1
```

系统需要把结果作为下一轮的上下文交回模型。仅把报错写到服务器日志，模型是看不到的。

于是，一次完整的工具交互有六个可分别测量的事件：

```text
原始输出出现调用候选
  → 调用被 parser 接受
  → 工具名和参数通过校验
  → 执行器实际运行
  → 产生 observation
  → observation 进入模型的下一次输入
```

“有工具输出”和“模型收到工具输出”也应该区分。消息拼接错误、上下文截断，都可能使最后一条边失败。

### 2.5 一张检查表

| 你看到的证据 | 现在能说什么 | 还不能说什么 |
|---|---|---|
| HTTP 200 | API 请求完成 | 有工具调用 |
| 原文出现 `run_tests` | 有相关文本 | 一定是调用；可能是讨论或复述 schema |
| JSON 可解码 | 语法检查通过 | 工具合法、参数符合 schema、程序正确 |
| `tool_calls` 非空 | 服务端识别出调用 | 工具已执行 |
| 执行计数增加 | 到达被计数的执行入口 | 执行成功、反馈送达 |
| 下一轮输入包含 observation | 模型获得反馈 | 模型利用了反馈 |
| 最后通过测试 | 该轨迹满足所用测试 | 对所有可能输入正确、具有通用修复能力 |

## 3. 模板、协议、解析器和约束分别做什么

### 3.1 Chat template：把结构化消息变成模型的输入

API 客户端发送 `system/user/assistant/tool` 消息对象，但模型实际读取的是 token 序列。chat template 把角色、内容、工具 schema 和特殊标记拼成具体文本。

模板可以告诉模型“你有这些工具”，还可以示范“调用请写成这种格式”。工具 schema 在 API 请求里存在，不等于模板最终把它放进了模型上下文。参考 [Hugging Face 的 chat template 说明](https://huggingface.co/docs/transformers/v4.43.0/chat_templating)。

模板是模型输入的一部分。因此换模板可能改变**首轮代码内容、调用概率、输出长度和格式**，绝不是天然只影响首轮以后的东西。

项目里曾写“adapter 只能影响第一轮之后，因此 53 vs 53 识别了失败层”。这句话不严谨：adapter 包含模板时，第一轮也可能改变。总通过数相同，还不能证明逐题生成相同。

### 3.2 Parser：把输出变成动作对象

Parser 规定哪些文本算工具调用。最简单的例子是先找信封标签，再对内部内容执行 JSON 解码，最后提取 `name` 与 `arguments`。

```text
<tool_call> ... </tool_call>   Hermes 常见的信封
<tools> ... </tools>           项目使用的第三方 dedicated adapter 所处理的格式之一
```json ... ```                Markdown 中的 JSON 代码块
裸 JSON                       没有额外标签的 JSON 对象
```

这些格式不等价。Parser 也可能支持未闭合标签、流式片段、多次调用等特殊情况。必须比较所用版本的真实实现，不能根据名字相同就认为行为相同。

解析器认可一段文本，仍不代表里面的工具名已声明。当前 `probe_react_full.py` 会再检查名称；`qwen_tools_parser.py` 的 verl 注册实现还会检查参数中存在非空 `code` 字符串。

### 3.3 Schema：约束形状，不验证算法正确性

三个检查逐层增强：

```text
JSON 合法
  → 符合工具 schema
  → 程序通过本题测试
```

`{"code":"return 123"}` 可以是合法 JSON，也可以符合“code 是字符串”的 schema，但程序本身可能语法错误或答错题。

把题目函数错当工具，则是另一类问题：可能 JSON 完全合法，却违反工具名单。

### 3.4 `auto`、`required` 和 `strict` 是不同的开关

| 设置 | 大体控制什么 | 实验中要注意什么 |
|---|---|---|
| `tool_choice="auto"` | 允许模型自行决定是否调用 | 没调用可能是合理选择，也可能是未识别 |
| `tool_choice="required"` | 要求产生工具调用 | 可能走不同的约束生成路径，不是原 auto 条件的等价复测 |
| 指定工具名 | 要求调用选定工具 | 不再测试自主工具选择 |
| `strict: true` | 在支持的实现中加强 schema 约束 | 具体支持范围依赖 parser、后端、版本和全局配置 |

vLLM 的相关机制可查[官方工具调用文档](https://docs.vllm.ai/en/stable/features/tool_calling/)。该文档会更新；解释历史实验时，仍以我们固定的 vLLM 版本、启动参数和请求原文为准。

一个特别容易犯的错：`required` 成功，不能说明 `auto` 下模型一定会调用，也不能独自证明 `auto` 的 parser 一定正常。它提供的是一条受控的阳性检查。

同理，`strict` 修复 wrong-tool 输出，说明约束改变了可生成／可接受的行为；不能证明模型内部对角色的理解已经改变。

### 3.5 FC 与 ReAct

Function Calling（FC）通常通过结构化工具声明和结构化返回字段连接系统。ReAct 是让推理与环境动作交替发生的方法，原始工作见 [ReAct 论文](https://arxiv.org/abs/2210.03629)。

我们实现的 ReAct 用文本协议表达动作，例如：

```text
Thought: I should check the implementation.
Action: run_tests
Action Input: def add(a, b): return a + b
```

宿主程序解析文本并执行。它绕开的是服务端的 FC parser，**没有绕开一切解析规则**，也不保证任意模型都能稳定遵从。

“FC 比 ReAct 差”可能来自多种差别：提示词、模板、生成约束、解析覆盖范围、token 预算、工具错误处理、停止规则。只有这些差别控制清楚，才能解释协议效应。

### 3.6 本项目有两个“adapter”，别混淆

- **Serving adapter**：本文大多数实验中指 parser 与 chat template 等服务配置的组合。
- **LoRA adapter**：训练时加入模型的可训练低秩参数。

前者可以不改模型权重；后者就是训练得到的权重增量。看到 “adapter repair” 要先问它指哪个。

## 4. 我们真正研究的问题

### 4.1 测量函数也是系统的一部分

假设模型根据历史 `h` 产生原始输出 `y`，接口规则 `I` 把它映射为动作 `a`：

```text
y ~ πθ(· | h)
a = I(y)
o = Environment(a)
```

评测器如果只数 `a`，就无法还原所有关于 `y` 的信息：多个不同的原始输出可以映射到“没有动作”。这像一个有信息损失的测量过程。

一个有限而清楚的例子：

```text
原文 A：直接给最终答案              → tool_calls=[]
原文 B：裸 JSON 中提交了工具调用     → tool_calls=[]
原文 C：复述工具说明但没真正提交     → tool_calls=[]
原文 D：带信封但 JSON 损坏           → tool_calls=[]
```

仅凭空字段无法识别原因。保留原文、验证参数、做受控重解析，可以恢复其中一些区别。不要把模型“想不想调用”的心理解释直接当成可观测量；我们实际测的是输出文本和系统行为。

### 4.2 “Censoring”在这里是什么意思

论文借用 censoring 描述行为在进入下游轨迹以前被接口过滤。它是与统计删失类似的测量问题表述，不意味着已经证明某个标准生存分析模型适用。

比较稳妥的核心表述是：

> 观察到的工具使用率依赖模型与接口组成的系统；接口不匹配可能让可识别的调用尝试没有进入执行与反馈通道。

不能把“任何失败”都叫同一种 censoring。没有调用意图、参数损坏、错工具、解析不匹配、执行器缺依赖，它们需要不同处理。

### 4.3 Masking 与 suppression

**Masking 案例：**模型输出了一段满足明确调用判据的文本，但下游接口没有把它转成动作。Qwen 的信封不匹配是本文的重要案例。

**Suppression 案例：**更强的约束使不合法的工具选择不再出现在相应输出中。Llama 的 strict 对照属于这个方向。

两者都说明接口会影响有效动作通道，但一个是损失本可利用的调用候选，一个是限制无效输出。不要为了统一术语，声称它们具有完全相同的因果结构。

### 4.4 一个实验可以回答三种强度不同的问题

| 问题 | 所需证据举例 |
|---|---|
| 这个条件下观察到什么？ | 原始输出、解析计数、执行日志 |
| 哪个接口改动造成了变化？ | 同题配对、受控更换组件、离线同字节重放 |
| 修复是否让模型学会了新能力？ | 完整训练对照、训练前后固定评测、正确的权重同步与统计分析 |

我们有较丰富的前两类证据。第三类不能从“工具终于执行了”直接推出。

## 5. 数据、benchmark、harness 与 verifier

### 5.1 四个对象的分工

| 对象 | 功能 | 本项目例子 |
|---|---|---|
| Dataset | 提供问题、参考信息与测试 | KodCode、EvalPlus 数据、BFCL cases |
| Harness | 组织请求、执行、轨迹和评分 | 自研 probe、BFCL handler、τ-bench runner |
| Executor | 真正运行程序或环境动作 | Python 测试进程、retail API |
| Verifier/scorer | 判断结果是否符合评价标准 | 测试通过判据、BFCL scorer、τ-bench 状态判据 |

用官方数据，不自动等于使用完整官方评测协议；使用官方 scorer，也不意味着自定义路由没有影响。论文需要把保留和修改的部分交代清楚。

### 5.2 KodCode 与 EvalPlus 在这里承担不同角色

代码训练和自研工具调用 probe 使用题目及测试；历史主要工具对照共享去重／清理后固定的 `clean[:100]` 样本。这让逐题配对成为可能，但它不是随机抽样的 100 题。

EvalPlus 用增强测试检查代码正确性。它加强的是测试覆盖，不会让“通过所有测试”变成数学意义上的程序正确性证明。参见 [EvalPlus 原论文](https://arxiv.org/abs/2305.01210)。

训练集、验证集、最终报告集要分开。增强测试覆盖与排除训练—评测污染也是两件事：测试多，不等于数据无泄漏。

### 5.3 题目数、测试数、轨迹数不要相加

一道题可以有多个测试；一条轨迹可以包含多次模型生成；一个训练 prompt 可以采样多条轨迹。

```text
task      题目身份
trial     对同一题的一次独立尝试
rollout   一次采样得到的交互轨迹
turn      轨迹中的一轮交互，具体定义由实现决定
generation 一次模型生成调用
test case 检查某个程序行为的一个测试输入／断言
```

仓库历史出现过 `540`、`542`、`454`、`996`、`1108` 等分母。它们不应靠记忆拼成一个统一故事。

当前 `CodeEvalHook` 加载 HumanEval+ 和 MBPP+，另用固定修复 probe 的 ID 交集构建 repair 通道。实际分母必须从那次 run 的 task manifest 与去重记录确认。旧文档把 `319/677` 写作 benchmark 题数，不能继续引用。

### 5.4 两种代码评测模式

当前 `sandbox.py` 有两个重要路径：

- `mode="pytest"`：面向相应训练测试，解析通过、失败、错误等数量，用于 partial credit。
- `mode="script"`：按 EvalPlus 记录拼装测试脚本，通过进程结果得到严格成败。

若拿 pytest 去收集一个不含 pytest 测试函数、而是脚本式 `check(candidate)` 的测试，可能“没有测试运行”。程序退出、没有抛异常、真正检查过题目，是不同事实。

### 5.5 训练奖励与评测正确率

当前训练 `reward_code.py` 提取最后提交的代码，运行测试，返回 `pass_ratio`。简化为：

$$
R = \frac{\text{passed}}{\text{passed+failed+errors+skipped+xfailed+xpassed}}.
$$

这是当前 `sandbox.Result.total` 的保守计数政策。没有测试时奖励为零。评测的 `all_passed` 还要求执行状态正常、至少运行了测试、通过数等于总数。

教学例子：10 个测试通过 7 个，训练奖励可为 0.7，但严格任务成功记为 0。平均奖励上涨，可能只是更多题从 2/10 变成 5/10，完全通过的题数未必上涨。

“给做错的题负奖励”不是本项目奖励函数的准确描述：原始奖励主要在 0—1 之间；经过组内比较以后，advantage 才可能为负。

### 5.6 我们的 verifier 有什么边界

项目早期的 pytest 摘要解析过于宽松，且 skipped/xfail 未计入分母。当前本地代码已有摘要行匹配和扩大分母的修复。

但修了这两处，不意味着已经得到不可利用的安全验证器：摘要仍来自同一执行过程的文本，执行隔离也不是完整的安全沙箱；测试覆盖、退出状态、环境权限和报告真实性仍要分别审计。源码中“never model-controlled output”之类注释，比实际能保证的东西更强。

Linux 资源限制、超时和独立临时目录主要控制故障影响，不构成对任意不可信程序的完整隔离。不要把生产机密放进实验执行环境，再仅凭这些限制运行任意代码。

重要区别是：**发现可被利用的缺口**，不等于**已证明模型在历史训练中利用了它**；日志没有发现利用迹象，也不等于排除了利用。

## 6. 三条看起来相似、实际上不同的代码路径

### 6.1 自研 FC serving probe

```text
probe_react_full.py
  → HTTP 请求带 messages / tools / tool_choice
  → vLLM 渲染模板并生成
  → vLLM parser 提取 tool_calls
  → probe 检查工具名与参数
  → sandbox.run_tests
  → probe 把 observation 放回消息
```

这里，服务端 parser 是动作通道的一部分。改 vLLM 的 `--tool-call-parser` 可能影响执行率。

### 6.2 真正的训练 rollout

```text
launch_ppo.py / verl trainer
  → 根据数据行的 agent_name 选择 AgentLoop
  → rollout backend 生成 token
  → verl 自己的 ToolParser 解析
  → ToolAgentLoop._call_tool
  → CodeTool.execute
  → 工具反馈回到 rollout 上下文
  → reward_code.compute_score
  → advantage / loss / update
```

这是本项目最容易忽略的一层：**verl parser 与 vLLM API parser 是两个实现入口。**两边都叫 `hermes`，也不表示注册表、正则和返回类型相同。

所以，把插件注册进 vLLM，不会自动修复 verl 的 AgentLoop。我们写的 `qwen_tools_parser.py` 要在 verl 的工具解析注册表里生效，还要确保 Ray worker 进程里也注册了。框架层概念可对照 [verl Agent Loop 文档](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)。

### 6.3 当前分解评测器：程序主动提供测试反馈

代码核对得到：`CodeEvalHook → ChatPolicy → eval_decompose.evaluate` 走的是另一条路径。

`ChatPolicy` 发普通 messages 请求，不提交 `tools`。`eval_decompose.evaluate` 取模型生成代码，**由评测器运行测试**，然后以新的 user 消息把错误交给模型。

```text
模型写代码
  → 评测器无条件运行测试
  → 评测器发“测试结果……请修正代码”
  → 模型再写代码
```

这个设计能测试**在获得外部反馈的条件下，模型会不会修复**。它不直接测试模型是否自主发起 FC，也不能把它的多轮数当作原生 AgentLoop 的调用轮数。

这条路径不必被视为无用。两种训练后的模型都通过同一个反馈评测器测试，可以帮助比较反馈利用能力。关键是把它称为统一的修复评测条件，并另测自主工具行为。

### 6.4 两次调用同一个 sandbox，含义可能不同

`CodeTool.execute` 调测试，是模型动作带来的环境交互；`reward_code.compute_score` 调测试，是训练器给最终答案打分。

如果你只统计 `sandbox.run_tests` 总调用数，会把两类混在一起。即便模型一次工具都没用，奖励计算照样能运行很多次测试。

因此我们在 AgentLoop 和 CodeTool 的调用边界加计数。学习时请反复问：**这是给模型看的反馈，还是只给优化器看的奖励？**

## 7. 怎么读我们的指标

### 7.1 三个任务级结果

对同一题的一次交互尝试，定义：

- `turn1_pass`：第一份程序通过所用测试。
- `final_pass`：轨迹的最终结果通过。
- `rescued`：第一轮未通过、最终通过。

教学例子：100 题，首轮过 53 题，另有 9 题经反馈后通过，且首轮过的题没有回退，则最终过 62 题。

一般情况下还要考虑回退：

$$
\text{final passes} - \text{turn1 passes}
= \text{rescues} - \text{regressions}.
$$

只有确认成功后停止、没有回退时，差值才等于 rescue。`eval_decompose` 当前成功即停止，满足这个结构条件；换一个会继续操作的 benchmark，就不能直接沿用。

### 7.2 两种 rescue 分母

```text
rescues / 全部任务数       多轮对总体通过率的贡献
rescues / 首轮失败任务数   在已有失败机会中救回的比例
```

二者都可有意义，但跨模型比较第二个指标时，失败题集合会变化。更强的模型可能只留下更难的失败题，条件修复率低不代表绝对修复能力更差。

所以我们还构建固定 buggy 初稿的 repair 通道，让不同 checkpoint 面对相同错误。它回答的是受控修复能力，不能与从零生成的 multi 通道直接合并。

### 7.3 `pass@1` 不一定意味着只生成过一次

代码生成文献中的 pass@k 通常针对多个候选解的成功情况。本项目部分历史字段把一次完整交互尝试的最终成功也记作 pass@1。

必须说明预算：是一份无反馈初稿，还是最多四轮、有测试反馈的一次 Agent 尝试。不能把后者与公开无工具单轮分数直接比较，哪怕都叫 pass@1。

### 7.4 四种调用率

| 指标 | 分子 | 常用分母 |
|---|---|---|
| first parsed | 每题第一次请求被解析的题数 | 题数 |
| any parsed | 整条轨迹至少解析一次的题数 | 题数 |
| parsed calls | 调用对象数量 | 要明确：请求数、generation 数或题数 |
| executed tasks | 至少实际执行一次工具的题数 | 题数 |

例如 τ-bench 修复臂 636 次调用发生在 115 题内，不是“636% 的任务调用了工具”。其中 103 题至少执行过一次，这才是相应的任务级覆盖率。

### 7.5 漏斗可以测，但分母和集合必须对齐

直觉上可以画 emitted → parsed → executed → observation → success。但真实日志可能包含重试、多调用、一题多轮。不能把不同单位的汇总数字硬画成严格递减的一组柱子。

本项目还存在观测限制：解析成功后，调用被移入 `tool_calls`，普通 `content` 可能为空。如果只保存 API 响应字段，就不能用空 content 推出模型没有原始调用文本。

正确的记录粒度应允许联结：

```text
run_id / arm / checkpoint / task_id / trial_id / rollout_id / turn_id / call_id
```

不是每份历史产物都有这些字段。缺失关联时，就诚实报告能够成立的聚合计数，别声称已经逐条闭合整条链。

## 8. 把每个实验当成一道推理题

这一章按科学问题排列，不按开机器的时间排列。实验编号有历史混用：`p3/` 既保存早期 rollout 探针，也保存后来的正式训练；`p6/PLAN_P3.md` 是后续训练方案。不要只凭 P 编号判断实验性质。

### 8.1 起点：训练曲线为什么值得拆开

**问题。**我们原来想知道，结果奖励能否让代码模型更善于利用测试反馈。

**历史报告。**1.5B 的 150-step 实验中，最终通过率数值上提高 2.6—2.8 个百分点；对应报告的 p 值为 0.064／0.078／0.077，未达到 0.05。新增通过题里 91—94% 首轮就过，多轮救回约为 6—9/540。

**推理。**总体分数的数值提高，主要出现在更好的初稿上。这促使我们排查工具交互，而不是已经证明“RL 有效但修复无效”。三个 p 值不显著，也不能因为方向相同就自动合成显著结论。

**证据边界。**历史 1.5B 训练没有保留足够完整的原始 rollout，后来不同设置的原文不能补回它当时到底说了什么。1.5B mandatory probe 的错误工具行为，也不应被改写成已验证的训练内有效调用损失。

### 8.2 Qwen2.5-Coder 规模梯子：观察值恒零时漏掉了什么

**设计。**同一批 100 题，同一类 optional 工具提示和 Hermes 配置，比较五个 Coder checkpoint。

| 尺寸 | first server-parsed | tight 调用候选 | 最终通过 |
|---|---:|---:|---:|
| 1.5B | 0 | 0 | 31 |
| 3B | 0 | 4 | 37 |
| 7B | 0 | 21 | 53 |
| 14B | 0 | 36 | 53 |
| 32B | 0 | 80 | 68 |

来源：[意图分类脚本](../analysis/intent.py)、`runs/final/traj_v5_Qwen*_fc_intent.jsonl`，以及论文中的规模表。

`tight` 是本项目较严格的启发式调用判据，不是每条均经 JSON/schema/执行检查的证明。人工裁决样本中，该层 precision 为 0.900，因此 80 × 0.900 ≈ 72 是假设 precision 可转移时的敏感性估计。它没有补回假阴性，也没有消除抽样误差，不能当成精确真实调用数或严格下界。

**可讲的发现。**在这个家族、任务样本和错配接口里，server-parsed 始终为零，而 tight 调用候选数随 checkpoint 大小增加。

**不可讲的结论。**“任何大模型都会被更多地隐藏”“参数规模造成了接口失效”“80 条全部合法可执行”。server 列恒零，增长来自 emitted 判据那一列；它可能混合了调用倾向、JSON 规整程度、任务能力等因素。

历史原文有 4000 字符存储上限，会使某些完整调用无法从保存的片段里检出。对该检测器而言，截断可能造成漏检；**有误报的检测计数并不因此自动成为真实有效调用数的严格下界**。截断与分类误差要分开考虑。

### 8.3 随机 300 题复现：样本选择会不会决定故事

固定的 `clean[:100]` 适合所有臂共享，但可能具有排序偏差。P0 用随机 300 题补测，记录见 [p0_random_300.json](../analysis/p0_random_300.json)。

五个 Coder 尺寸的 tight 数为 `0、13、90、119、242`，server-parsed 仍为零。7B 的比例从原来的 21/100 变为 90/300 = 30%。这说明具体幅度依赖样本，不能只保留最顺眼的一张旧表。

7B 的修复比较中，最终通过为 160/300 → 178/300，两个方向的不一致题数为 43 与 25，报告的 exact p≈0.0385。这是名义 0.05 阈值下的证据；在论文采用的多重比较讨论下，没有越过更严格阈值。

新的 1500 个“题目×尺寸”观测，来自 300 个共享题目，不是 1500 个独立任务。复现强化的是在所抽样数据池中的稳健性，不是对任意代码任务的泛化证明。

### 8.4 离线重解析：同样的字节，换一条识别规则

**问题。**是模型根本没有输出任何调用候选，还是特定规则不识别它？

**做法。**保存原文后，不再调用模型，而是把同一段文本交给不同的识别规则。这种比较固定了生成结果，可以隔离这些规则对已观察文本的影响。

但如果某个宽松 parser 能从自然语言里的示例中抓出调用，也会增加误报。重新解析必须同时确认：工具名、参数、示例／真实提交区别，以及执行前的合法性检查。

因此，离线“能抽出 100 个对象”与在线“模型能正确使用 100 次工具”不是一个结果。

项目的 [failure_layer.py](../analysis/failure_layer.py) 汇总曾报告 4254 个去重 first turns 中没有 `parser_loss`。这是该重放规则和样本下的结果；不能升级为“所有 serving stack 都没有 parser bug”。不同 parser、流式／非流式分支和版本需要分别验证。

尤其注意：此分类器首先检查信封，缺失就返回 `no_envelope`。这只定位第一道失败条件，不能判断后面的 payload 是否也损坏。

### 8.5 P1：BFCL 提供第三方数据和评分

BFCL 测量函数／工具调用，在不同类别中使用相应的检查与评分方式。我们选择固定版本下 `simple_python` 与 `multi_turn_base` 各 100 题，而不是跑完 BFCL v4 的所有类别。官方全套 benchmark 的组成可查 [BFCL v4 介绍](https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html)。

**为什么重要。**如果问题只在自研小任务里发生，可能是我们的 harness 写得奇怪。使用 BFCL 自己的数据、相应 executor 和 scorer，可以检验它是否超出自研任务。

**改了哪里。**本项目通过 OpenAI-compatible handler 把请求送进 serving parser 路径。BFCL 原有部分本地模型 handler 会绕过这个路径。我们研究的是指定 serving 路径的效应，不是在证明所有官方默认入口都发生同一种问题。

**两条对角臂的结果。**

| 指标 | documented 配置 | dedicated 配置 |
|---|---:|---:|
| 200 题首请求解析 | 0 | 196 |
| `simple_python` 类别分数 | 0.00 | 0.96 |
| `multi_turn_base` 类别分数 | 0.00 | 0.19 |
| multi-turn 100 题中执行过工具 | 0 | 98 |

这说明配置能大幅改变这个模型在指定 benchmark 路径下的可观察调用和得分。`0.96` 是类别结果，不能说是完整 BFCL 排行榜总分。`0→0.19` 也没有跨越整个 0—1 值域；接近全跨度的是 simple_python 的变化。

数据与配置索引：[p1/](../p1/)、[runs/p1_clean/](../runs/p1_clean/)、[runs/p1_2x2/](../runs/p1_2x2/)。

### 8.6 BFCL 2×2：如何读最关键的一张表

| 模板 × parser | Hermes | dedicated parser |
|---|---:|---:|
| documented template | 0/200 | 0/200 |
| dedicated template | 0/200 | 196/200 |

这张表说明：从左上角出发，只换一边均未恢复；两边配套更换才得到 196/200。

设 A 为 dedicated template，B 为 dedicated parser，四格解析率为：

$$
y_{00}=0,\quad y_{10}=0,\quad y_{01}=0,\quad y_{11}=0.98.
$$

**在 baseline 上的简单效应：**

$$
y_{10}-y_{00}=0,\qquad y_{01}-y_{00}=0.
$$

**交互对比／差分之差：**

$$
(y_{11}-y_{01})-(y_{10}-y_{00})=0.98.
$$

**对另一因素平均后的 A 主效应：**

$$
\frac{y_{10}+y_{11}}{2}-\frac{y_{00}+y_{01}}{2}=0.49.
$$

B 的平均主效应同样是 0.49。因此正文不应无定义地写“两个主效应精确为零”。使用 baseline 编码的回归项和报告平均主效应，是不同约定。

你不需要在面试时背回归式。说清楚“单独换任一组件都没有从 baseline 救回，匹配组合才恢复”就已经准确而有力。

这张表也不能自动证明：每个组件没有 bug、全部题的 payload 逐字相同、没有别的配置能更好。我们固定的是模型权重，不是模板改变后必然相同的模型输出。

### 8.7 P2：Instruct 同谱系对照

**问题。**Hermes 是否对整个 Qwen2.5 谱系都无效？

**做法。**换为 Qwen2.5-Instruct 的五个尺寸，保持相应任务与 serving 条件，对照 Coder 梯子。

| 尺寸 | first parsed | 首轮通过 | 最终通过 | 救回 |
|---|---:|---:|---:|---:|
| 1.5B | 1 | 13 | 13 | 0 |
| 3B | 11 | 14 | 17 | 3 |
| 7B | 63 | 34 | 40 | 6 |
| 14B | 77 | 38 | 52 | 14 |
| 32B | 88 | 42 | 65 | 23 |

**解释。**同谱系的 Instruct 不呈现 Coder 的 flat-zero parsed pattern，因此不能把结果归因于共享 family/template 名称本身。

| 官方模板 FC | 95 | 22 | 73 | 33 | 44 |

这个实验很好地说明约束可以减少无效工具输出。它没有证明模型内部角色理解被治好了，也不能由“一个开关有效”推出“其它机制都已排除”。

其它材料包括压力提示、采样方差、both-parsed 条件分析、成功集合的 Jaccard／组成漂移，以及 Mistral 和 DeepSeek 的边界排查。它们分别帮助发现提示敏感性、随机性、题目组成变化和环境错误，不应统一包装成独立的“机制复制”。

尤其 Mistral 的多臂请求错误记录可以支持错误率分析，却不支持把缺失响应当作模型能力失败的通过率对照。DeepSeek 的模板检查证据也不能替代完整推理实验。

## 9. 从你熟悉的梯度下降理解 Agent RL

### 9.1 SFT 和 RL 优化的信号不同

SFT 给定输入和目标输出，对目标 token 做交叉熵训练。RL 则让当前策略生成结果，再用结果的 reward 调整生成这些输出的倾向。

程序测试器不可微没有关系。RL 不需要把梯度穿过 pytest 或整个环境，它利用生成动作的 log probability 和获得的回报构造梯度估计。

把一条轨迹记为 τ，最简化的目标是：

$$
J(\theta)=\mathbb E_{\tau\sim p_{\theta,I}}[R(\tau)].
$$

这里特意把接口 `I` 放进轨迹分布。相同模型输出在不同接口下可以进入不同环境分支，收到不同反馈，从而影响后续输入和采样结果。

### 9.2 Policy gradient 的直觉

一个省略基线、KL、裁剪和 token mask 的教学表达式：

$$
\widehat{\nabla J}
=\frac1N\sum_i A_i\sum_{t\in\text{model-generated tokens}}
\nabla_\theta\log\pi_\theta(y_{i,t}\mid h_{i,t}).
$$

`A_i` 表示这条样本相对某个基准有多好。正 advantage 倾向于提高这类已采样输出的概率，负 advantage 倾向于降低它。

环境 observation 虽然进入上下文，通常不能被当成模型自己采样的 action token 来优化。对训练 loss 的 token mask 是否正确，是多轮训练的重要实现检查。

“给整条轨迹同一个 reward”并不意味着已经定位出哪一轮修改有功。这正是 credit assignment：好结果应该归功于选工具、初稿质量、读报错，还是某次幸运采样？

### 9.3 Actor、reference、critic 不要混

| 角色 | 功能 |
|---|---|
| actor/policy | 正在优化的生成模型 |
| rollout policy | 产生当前训练样本的策略快照／推理副本 |
| reference policy | 用于约束偏离程度的参考模型，是否启用及方式依配置 |
| critic/value model | 估计状态／序列价值的模型，某些算法使用，GRPO 可不另训这个模型 |
| reward function | 给样本打分；本项目主要是程序测试，不必是神经网络 |

日志路径叫 `critic/rewards/mean`，不自动证明真的训练了一个 critic 网络。要看算法配置和实例化代码。

### 9.4 GRPO：同一道题的多份输出相互比较

GRPO 的核心做法之一，是对同一 prompt 采样一组输出，用组内 reward 比较估计 advantage，从而不必依赖独立训练的 value critic。原始方法见 [DeepSeekMath](https://arxiv.org/abs/2402.03300)。

教学例子，同一道题四次采样奖励为：

```text
样本       A     B     C     D
reward     0     0.5   0.5   1
组内均值               0.5
减去均值  -0.5   0     0     0.5
```

一种常见形式继续除以组内标准差：

$$
A_i=\frac{r_i-\bar r}{s_r+\epsilon}.
$$

如果四个样本全是零，组内没有相对优劣，reward-derived advantage 便为零。这解释了为什么 partial credit 可能有帮助：若样本分别通过 2、4、5、7 个测试，就有了可区分的信号。

但有三个限定：

- partial credit 不保证产生有用的工具使用策略，可能主要改善初稿。
- “组内 advantage 为零”不等于整个训练 loss 的所有项都为零；KL 等项仍可能影响更新。
- GRPO 有标准差、长度归一化和裁剪等实现变体。学习上述直觉即可，不要凭算法名字猜本项目具体公式。可参照 [TRL 的 GRPO 实现说明](https://huggingface.co/docs/trl/grpo_trainer)，实际配置仍应回到所用 verl 版本。

### 9.5 RLOO：比较除自己之外的样本

RLOO 的一个核心基线是同 prompt 下其余样本的平均 reward：

$$
A_i=r_i-\frac{1}{G-1}\sum_{j\ne i}r_j.
$$

仍用 `[0,0.5,0.5,1]`：第一个样本相对其它三个的均值更差，最后一个更好。它属于 REINFORCE 风格的方差降低方法，不必为了这个项目先推导所有优化变体。参考 [RLOO 原始工作](https://arxiv.org/abs/2402.14740)。

GRPO 与 RLOO 都需要清楚地知道：一组样本是否来自同一个题目、reward 是否真实、哪些 token 由模型生成。接口错误会影响它们实际拿到的交互经验。

### 9.6 PPO clipping 和 KL 为什么出现

训练器可能对同批 rollout 做多个 minibatch 更新。更新后的策略与产生数据的旧策略逐渐不同，因此常用新旧概率比和裁剪限制某些过大的更新。

简化的 PPO surrogate 为：

$$
\min\left(\rho_t A_t,\operatorname{clip}(\rho_t,1-\epsilon,1+\epsilon)A_t\right),
\quad
\rho_t=\frac{\pi_\theta(y_t\mid h_t)}{\pi_{\mathrm{old}}(y_t\mid h_t)}.
$$

KL 正则常用于约束策略相对参考策略的偏离。裁剪不保证模型永不变坏，KL 也不保证获得工具能力。它们解决优化稳定性问题，不会自动修复执行路径。参见 [PPO 原论文](https://arxiv.org/abs/1707.06347)。

### 9.7 为什么工具不执行，reward 仍能提高

在本项目中，reward 函数会提取最终代码直接运行测试。因此完全可以发生：

```text
模型未成功调用工具
  → 直接给出代码
  → 训练器的 verifier 跑测试
  → 得到正 reward
  → 更新代码生成策略
```

这条路径没有真实的“读取测试反馈后修复”经验，但有代码正确性的训练信号。因而奖励曲线健康不能代替工具路径监测。

也不要走到另一个极端，说“没有工具成功轨迹，模型永远不可能学会调用”。参数共享、其它样本、语言模式变化、约束和探索，都可能使未来行为变化。有限样本的零不证明策略支持集里概率为零；后续 broken run 的 7 次接受就是必须保留的观察。

### 9.8 Cold-start hazard 应该怎么理解

一种合理的实践担忧是：如果有价值的工具反馈很少进入采样经验，而直接答案一直能拿分，优化可能持续偏向直接回答，难以获得我们希望训练的修复经验。

这是机制解释／待检验的训练风险。要把它变成“接口导致最终修复能力受损”的因果结论，需要对照训练与正确的固定评测，而不只是把一张工具计数表放在 reward 曲线旁边。

## 10. P3 应该测什么，怎样才不再跑错问题

### 10.1 三个互相独立的验收问题

1. **通道恢复了吗？**正确工具调用被接受、执行，observation 回到了下一轮输入。
2. **模型行为变了吗？**相同评测条件下，训练后更常正确选择工具或更善于利用反馈。
3. **任务结果提高了吗？**固定任务集上最终成功／rescue 有可支持的变化。

第一个成立，不自动带出后两个。学习文档中的“机制恢复”专指第一类，不含有默认的成功率承诺。

### 10.2 最小的干净训练对照

同一个初始 7B checkpoint，两个 LoRA 训练臂，固定数据、prompt、schema、reward、训练步数、样本预算和相应 seed 设置。

```text
broken  : verl multi_turn.format = hermes
repaired: verl multi_turn.format = qwen2_5_coder
```

当前实现是在相应进程内注册自定义 parser，再通过配置选择它。所谓“只改一次注册”是概括说法；真正该比较的是两臂最终解析类、代码版本和其它运行条件。

### 10.3 为什么评测接口也要统一

设两个训练后的权重是 θ_broken 和 θ_repaired。

如果前者只用 broken parser 评测，后者只用 repaired parser 评测，看到差异时，你无法知道是**训练学到了不同策略**，还是**评测时一边仍然不能调用**。

优先做统一评测：

```text
θ_broken  ─┐
            ├→ 同一个可工作接口／同一个反馈评测器 → 比较学习结果
θ_repaired ─┘
```

同时另报各自原生路径下的部署结果。前者主要回答策略差异，后者回答完整系统表现。

当前 `CodeEvalHook` 是外部提供反馈的程序式评测，可用来测条件修复能力，但需要明确这不是自主 FC 路径。若要测自主工具选择，增加或使用对应的原生工具交互评测，分别命名指标。

### 10.4 为什么一定要 step 0

如果训练前 repaired 配置已经能完成很多工具动作，训练后的高分可能主要是接口即时改善，而不是 RL 增益。

至少比较每条臂训练前后的变化，并考察两臂变化之差。教学表达式为：

$$
\Delta_{\mathrm{learn}}=
(R_{\mathrm{rep,final}}-R_{\mathrm{rep,0}})
-(R_{\mathrm{broken,final}}-R_{\mathrm{broken,0}}).
$$

这里的 R 可以是统一评测下的 rescue 率，而非原始训练 reward。还需要逐题和 seed 的不确定性分析；差分公式本身不是显著性证明。

不能先看 repaired 涨不涨，再决定要不要补 broken，这会让实验设计受已观察结果影响。

### 10.5 不要用几种不正确的 A/B 分支

| 容易作出的判断 | 为什么不够 |
|---|---|
| reward 涨了，所以多轮学会了 | reward 可来自直接答案 |
| num_turns 涨了，所以利用了反馈 | 多轮可能只是重复、错误或循环 |
| repaired 比自己 step 0 好，所以 parser 造成学习 | 缺匹配 broken 趋势和统一评测 |
| p>0.05，所以修复也没用 | 可能样本太少，不能证明等价 |
| 7B repaired 学会了，所以 1.5B ReAct 历史观察被推翻 | 不同模型、协议、预算；被推翻的只能是超范围推广 |

### 10.6 开跑前必须能回答的技术问题

- 每次评测是否使用当前更新后的 LoRA，而不是初始 base 权重？要用权重／adapter 版本记录和同步检查验证。
- `test_freq` 是否真的触发目标评测，失败是否明确记录？装上 hook 不等于它运行过。
- 不同 arm、重试、step 的输出是否分目录？禁止同一文件混入重复评测再直接数行。
- `task_id + channel + trial + step + run_id` 是否唯一？不要用字典覆盖重复记录后假装数据干净。
- 是否有完整原文、parser 选择、接受对象和 observation 关联？sha256 验证完整性，不能单独证明事件归属正确。
- 每个 checkpoint 是否成功写完、能加载、能恢复 optimizer／step／RNG 等所需状态？

`save_freq>0` 只是保存设置，不保证完整恢复。当前历史 runner 默认目录复用且包含清理操作，`resume_mode=disable` 也存在；因此不能把它当成可直接重跑的安全操作手册。

### 10.7 P3 最终回答了什么

三个验收问题现在可以分别作答：

1. **通道恢复：是。** executed/observed 从 10 变为 16,844。
2. **策略在固定评测上的行为改善：没有测到。** repaired turn-1 由 418/542 变为 415/542。
3. **多轮结果提高：没有测到。** final 430/542 变为 427/542，rescue 12 变为 12。

这不是“实验失败”，也不是“已排除接口对学习的作用”。直接测到的是训练期间工具经验大幅增加，而这些训练经历没有在当前共同程序反馈协议下表现为可检测的收益。训练使用 tool-role 反馈，已有评估自动测试代码并通过 user message 反馈，存在协议迁移。因此不能进一步断言模型没有学到原生 FC 策略，或接口修复一般不足以带来学习。第 19 章的新评估正是为了检查这个尚未回答的问题，而不是重跑训练。

## 11. 显存、LoRA、checkpoint 和速度

### 11.1 为什么 7B 推理能跑，训练会 OOM

bf16 每参数通常占 2 字节，7B 参数的纯权重大约是 14 GB（十进制估算）。这只是模型权重，不是完整训练需求。

训练还可能需要梯度、优化器状态、激活、临时张量、参考模型；rollout 侧还需要推理副本和 KV cache。具体组件是否共存、如何分片和 offload，依赖实现。

所以不能用“80 GB 减去 14 GB 还有很多”估计 RL 是否能跑。也不能用 rollout 阶段的低显存占用保证稍后的 backward 安全。

### 11.2 LoRA 做了什么

对一个权重矩阵 W，LoRA 用低秩增量表示更新：

$$
W'=W+\frac{\alpha}{r}BA.
$$

基础 W 通常冻结，主要训练 A、B。它减少可训练参数及相关状态，但基础模型、激活、生成缓存不会凭空消失。参考 [LoRA 原论文](https://arxiv.org/abs/2106.09685)。

项目脚本可见 rank=32、alpha=32、all-linear 等配置；这描述当前脚本意图，历史 run 还要核对自己的启动配置和部署代码。

两个 arm 都使用完全一致 LoRA，有利于臂间比较。但不能不加说明就和早期不同尺寸的全参训练比绝对学习效率。

### 11.3 四个降低显存的办法

| 方法 | 节省什么 | 代价／边界 |
|---|---|---|
| LoRA | 可训练权重、梯度、优化器状态 | 不等于全参训练 |
| activation checkpointing | 少存部分中间激活 | backward 需要重算 |
| CPU offload | 将部分状态放 CPU 内存 | PCIe 传输和 CPU 内存压力 |
| 小 microbatch | 单次前后向激活峰值 | 速度下降，需要关注有效 batch |

训练 batch、PPO minibatch、microbatch、rollout.n 不是同一个参数。例：16 道 prompt，每题采样 8 条轨迹，计划 128 条轨迹；每轨迹可能多次 generation，故 generation 日志不必正好 128 行。

### 11.4 checkpoint 不能只看“目录出现了”

区分三种文件：

- 推理权重：用于生成。
- LoRA 增量：需要匹配基础模型才能解释。
- 训练态 checkpoint：除权重外，还可能包含 optimizer、scheduler、随机状态、数据位置等恢复信息。

历史一次 1-step 探针观察到 checkpoint 目录约 15 GB。这个观测不能保证写入已完成，也不能推广为每个 checkpoint 永远 15 GB。

磁盘预算应在确认完整写入后计算：基础模型与环境 + 保留 checkpoint + 新 checkpoint 写入重叠峰值 + 日志／数据／临时文件 + 余量。数据盘与系统盘要分别检查挂载位置。

`max_to_keep=2` 不代表最多只需要两个 checkpoint 的空间：先写新的再删除旧的，就可能短时占三个；保留配置还可能没有按预期生效。

### 11.5 怎么估时间才可靠

总耗时可分为：下载与启动 + rollout + reward 执行 + update + validation + checkpoint IO。

用当前环境已完成的完整 step 和 eval 测量估计，且分别统计；不要拿单纯 generation 吞吐估整个训练。修复后调用和上下文变长，repaired 的 wall time 与 broken 不一定一样。

这也是为什么“两条臂跑同样小时数”与“同样训练步数／rollout 预算”不是同一个控制条件。资源公平性需要事先定义。

## 12. 现在有哪些结论能讲，哪些必须先核查

### 12.1 按证据类型，而不是按“漂亮程度”理解项目

| 类型 | 当前材料 | 合理用途 |
|---|---|---|
| 服务／执行侧直接计数 | BFCL 解析与 scorer 结果，τ-bench 执行与任务记录 | 描述指定配置下的系统行为 |
| 有人工校准的启发式计数 | Coder tight 梯子、部分意图分类 | 描述调用候选与估计误差 |
| rollout 内的直接事件 | 两条正式臂最终有效路径的 accepted／execute 和原文 | 研究训练采样中哪些调用到达环境 |
| 需要重放验证的派生标签 | “完整调用”“parser_loss”“verl_would_accept” | 完成判据审计后再作强解释 |
| 已完成的单变量训练对照 | 匹配的 broken／repaired 7B LoRA 训练 | 机制强阳性；学习收益为设置限定的 null |

这不是说前面所有数字都要推倒重来。应该精确定位：错误发生在日志本身、事件计数、分类标签，还是把结果解释得太强。

### 12.2 需要清楚记住的八处边界

**第一，tight 不等于 JSON 合法。**`analysis/intent.py` 用正则寻找字段和代码关键词，没有 `json.loads`。例如字符串里含未转义换行，仍可能命中 regex。学习和对外表达时，称它为 tight-classified call candidate 更准确。

**第二，no_envelope 不排除 bad_payload。**当前分类器是按第一个失败条件分层，不是独立检测所有属性。“全部归到信封层”与“全部 payload 合法”不是同义句。

**第三，P3 的旧离线 verl 重放辅助函数曾有实现错误。**`VERL_RE` 只有一个捕获组，`findall()` 返回字符串；旧 `_accepts` 却取 `m[0]`，把首字符当完整 JSON。后续诊断实现已修正；使用新的诊断产物，不沿用旧派生标签。实际 parser 的 accepted 日志属于独立测量，不因辅助函数出错而自动作废。

**第四，不能把各 parser 下的数据统一拿 Hermes 重放，就证明各自的 parser 没 bug。**必须匹配实际注册类、版本、streaming 模式、token 解码和后续校验。

**第五，2×2 的零是 baseline 简单效应为零。**不要继续背“平均主效应全零”。

**第六，53 vs 53 不识别失败层。**相同总数不等于相同题目，模板也会改变初稿。它是观察到的模式，不是层定位定理。

**第七，旧探针零执行不是长期永不执行。**后来的 broken 正式臂接受／执行过 10 次。有限采样的零也不保证零概率。

**第八，旧 step 0 的 20/1108 已作废。**正式重跑使用 542 个唯一、配对的 multi
items，并逐 checkpoint 记录 run/channel/task/step 身份、内容哈希和 native weight step。
学习结论只读这套重建后的评测，不从历史 append 文件恢复。

这八处已在学习文档和论文中同步纠正；历史产物保持不变，正式重跑单独建目录并记录
恢复契约，避免把修复后的证据倒灌成旧实验当时就拥有的证据。

### 12.3 还有几个看起来谨慎、实际上仍过强的句式

- “新模型换对 parser 成功，所以旧 parser 实现一定没问题。”成功对照并不能免除实现审计。
- “ReAct 的 token 预算以前更小，修正预算只能让它更好。”更长预算不保证表现单调改善，必须看重跑。
- “有 98 行 preflight，所有静默失败都能被发现。”当前脚本主要做 auto／required 请求、工具名与参数检查，没有完成真实 executor→observation 的端到端测试。
- “正式臂一共有 50 条，所以有 50 个独立验证。”其中有不合格的能力比较臂，也有共享任务、共享条件；数量不能替代独立性和设计。
- “reward 平滑，所以没有 reward hacking。”没有明显异常不是排除漏洞利用的证据。
- “同一个 seed 就控制了所有随机性。”异步调度、数值实现、模拟用户和重试仍可能产生差异。

### 12.4 怎样表达自己的工作才稳

你可以说：

> 我搭建并审计了一个从模型输出到工具反馈的评测流程，在自研代码任务、BFCL 指定类别和 τ-bench retail 上比较接口配置，观察到解析和执行层的巨大差异；同时追踪了这些差异在训练 rollout 中的表现。对模型规模和 RL 学习效果，我分别报告了证据范围，没有把工具执行恢复直接当作学习成功。

这段话可以由现有工作支持，也为后续把判据检查得更严格留出了空间。

## 13. 你需要掌握的实验设计和统计

### 13.1 什么叫对照，只改一个参数就够了吗

你希望估计某个配置的作用，就要让比较臂在题目、模型、预算等其它重要条件上可比。

“命令行只改一行”不一定等于只改一个机制。比如换模板的一行配置，会同时改变工具说明、few-shot 和序列化格式；`strict` 的一个开关可能改变生成分布。

好的实验描述会列出实际改变的内容，并把它当成干预本身。BFCL adapter-level 干预有价值，不需要伪装成 parser-only。

### 13.2 为什么要同题配对

假设两种配置在同样 100 题上分别通过 49 和 61 题。仅看这两个总数，不能知道变化来自哪几题。

教学配对表：

| | 新配置通过 | 新配置失败 |
|---|---:|---:|
| 旧配置通过 | 46 | 3 |
| 旧配置失败 | 15 | 36 |

两边总通过分别为 49、61，净增 12。真正反映方向不对称的是：15 题被救回，3 题回退。

同样增加 12 题，如果不一致对是 30 vs 18，不确定性就不同。因此日志必须保留 task_id；只有总百分比不足以还原配对证据。

### 13.3 Exact McNemar 在检验什么

对二元配对结果，设两个方向的不一致题数为 b 和 c。在无方向差异的原假设下，可对 b+c 个不一致对使用参数 0.5 的二项分布进行 exact 检验。

教学表里的 15 vs 3 得到双侧 p≈0.00754。τ-bench 的 3 vs 0 得到 p=0.25。这也解释了为什么 7→10 看起来“只赢不输”，证据仍然有限：有方向信息的只有三题。

本仓库的不同分析脚本并不全用同一种检验：`analyze_step3.py` 里有连续性校正的近似形式。引用数字前要说明 exact 还是 approximate，别因为都叫 McNemar 就混用。

### 13.4 p 值不是效果大小，也不是结论为真的概率

效果大小回答“差多少”；p 值衡量在指定原假设及统计模型下，当前或更极端数据是否罕见。

`p>0.05` 可以来自效果小，也可以来自样本少、方差大。不能直接解释成没有效果。`p<0.05` 也不保证因果、数据干净或对新任务泛化。

应同时看：差值、配对数、置信区间、样本选择、多个检验以及运行是否有效。

### 13.5 多重比较为什么重要

如果检查很多指标、模型和切片，再只展示几个低 p 值，偶然“发现”的机会会上升。

本项目最终回顾性统计审计明确列出 27 项检验，把总体 0.05 分给每个检验：

$$
\alpha_{\mathrm{per\ test}}=0.05/27\approx0.00185185.
$$

所以 p≈0.0075 和 p≈0.00188 都不通过。判断应使用未四舍五入的值。早期“约 12 项”的阈值不是当前规则；这次明确列举属于回顾性审计，不能包装成运行前预注册的统计政策。

另一个更新是稀疏配对风险差区间：只有少数 discordant pairs 时，不依赖 Wald 正态近似，而使用基于精确二项界的保守构造。这个区间反映评估题目层面的不确定性，不包含训练种子差异和重新推理的变异。

它偏保守，但一个清楚的多重比较政策比“主文写显著，Limitations 再说有很多检验”更容易审计。

### 13.6 什么情况下“零”很有力，什么情况下不够

对已存字节，给定确定 parser 重放为零，是这些字节在该规则下的确定性结果。

但这些字节是从模型行为中采样得到的。要推广为“新题也几乎总是零”，仍有抽样不确定性。单题多轮或同题多次 generation 常相关，不能当作独立题目随意扩大样本量。

若要做任务级 confidence interval 或 bootstrap，应按研究问题保留配对和聚类结构；训练结果还要考虑 seed，而不只是把同一 seed 的上万 token 当作独立证据。

### 13.7 Post-treatment conditioning：为什么 both-parsed 要小心

如果只比较“两条臂都成功解析”的题目，你筛选的条件本身已受到接口影响。

例如新 parser 额外救回很多难题，这些题却被 both-parsed 子集排除。子集上的表现不代表原始全集，更不能自动作为“去掉接口影响后的纯协议因果效应”。

它可以是描述性分析，但需要明确筛选规则和剩余题目构成。

同一个原因也使“只对各模型自然失败题测修复率”难以公平比较；固定 buggy 初稿能缓解这个问题。

### 13.8 人工标注：precision 与 κ 各回答什么

`precision` 回答：被分类器判为正的样本，有多少经过人工判定确实为正。

`Cohen's κ` 是扣除按标签边际分布所预期的偶然一致后的协议一致度：

$$
\kappa=\frac{p_o-p_e}{1-p_e}.
$$

κ 高不表示判断一定正确：两个人也可能受同一显示截断影响。κ 与 precision 也不可互换。

本项目应记住的几个数字：

| 数字 | 对应对象 |
|---|---|
| κ=0.713 | 第一轮记录，受标注展示仪器问题影响 |
| κ=0.967 | 两名标注者看到相同字节的 62 项 |
| κ=0.871 | 分类器对第三方裁决 gold standard |
| 36/40=0.900 | 最终 tight 层 precision |

历史 0.950→0.975→0.900 的估计过程必须保留，不能只拿最大的那个值。校准样本经过分层抽样，不能假定各尺寸误报率必然相同。

80 × 0.9≈72 省略了 precision 的估计不确定性及跨尺寸转移误差，只是带假设的敏感性估计；它不恢复假阴性，也不是精确真值。

## 14. 按源码学习：每次只追一条数据流

### 14.1 第一次阅读：从 serving 请求追到执行

## 15. 以后开机前，你自己就能做的验收

### 15.1 写一张 run card

不必长，一页就能避免很多事故：

```text
科学问题：
主指标：
两条臂实际差异：
模型 / tokenizer / 模板 / parser revision：
数据 manifest 与 task 数：
seed / decoding / 上下文与输出预算：
训练步数 / rollout 数 / 评测步：
reward / executor 版本：
输出目录与 run_id：
checkpoint 保存、完整性与恢复验收：
哪些错误使哪一层指标失去解释资格：
```

不要把“机器开了”当成实验已经准备好。模型能下载、服务能启动，只完成了基础设施的一部分。

### 15.2 preflight 至少有三个层次

**接口检查。**请求带了工具，模板确实注入，已知合规文本可被正确 parser 识别，工具名和参数校验生效。

**执行检查。**一个已知能通过的程序、一个已知会失败的程序，都得到预期结果。确认测试确实运行，错误回到下一轮输入。

**训练检查。**小 rollout 能收集，完整 update 能完成，评测读到更新后的权重，checkpoint 写完并可恢复。只跑完 generation 不能验收训练。

当前 [preflight_toolcall.py](../preflight_toolcall.py) 主要覆盖第一层的一部分。它的正向检查有用，但一题 auto 不调用，也可能是模型选择直接回答；必须结合原文判断，不能自动给模型贴“错配”标签。

### 15.3 正确理解退出码和“无请求错误”

`rc=0` 只表示脚本按自己的逻辑正常退出。如果脚本没有检查 pytest 是否存在，没有检查产物数，没有检查解析钩子是否安装，它仍可能“正常结束”一个无法回答问题的实验。

P2 初次执行层的教训正是如此：请求错误为零，仍不代表工具执行环境正常。

应该分层记录：HTTP errors、parser errors、wrong tools、executor unavailable、test failures、observation failures。不要把环境故障统一归为模型失败，也不要把研究对象中的 parser 不接受本身一律当作无效实验。

### 15.4 “零执行”如何验证计数器不是坏的

不能要求 negative arm 的 execution hook 必须触发，否则真正零执行的臂永远过不了验收。

合理做法是：记录 hook 安装状态，在独立阳性检查中验证它会触发，再观察负臂的运行事件。安装记录、阳性功能检查、负臂结果，是三种不同证据。

### 15.5 数据完整性不只是保存全文

保存全文加哈希，可以检查文本是否后来改变、是否按记录长度保留。它不自动验证：

- 是否漏了一些 generation；
- 是否把两个 run 混在一起；
- task_id 是否错配；
- 模型看到的输入是否与记录一致；
- 观察计数是否来自正确的工具入口。

应同时保存最终配置、事件身份、代码版本和完成标记。不要把“有 sha256”当作整套实验已经完整可复现。

## 16. 不用 GPU 的练习与答案

### 16.1 运行配套练习

在仓库根目录执行：

```bash
python3 -B writeup/learning_lab.py
```

它只用 Python 标准库，演示以下内容：

1. 同一合法裸调用为什么能被一条规则识别、被另一条忽略。
2. JSON 合法、工具合法、Python 语法合法、任务正确为什么不是一回事。
3. 2×2 的 baseline 简单效应、平均主效应和交互对比。
4. 组内相对奖励与救回／回退分解。
5. exact McNemar 的 15 vs 3 和 3 vs 0。

这个脚本是教学模型，不冒充生产 parser 或实验重算器。特别是“Python 语法合法”使用 AST 检查，不运行程序，也不判断程序语义正确。

### 16.2 十个基础问题

**问 1：模型在 content 里写了 run_tests，是否已经调用？**

没有。它可能在讨论工具，也可能输出了未被识别的候选。要继续检查文本、parser、参数、执行和反馈。

**问 2：required 成功，auto 为零，可以宣布 auto parser 坏了吗？**

不可以。它们可能走不同生成约束，模型也可能在 auto 下选择直接回答。检查原文和实际解析路径。

**问 3：工具执行次数增长，是否说明学会多轮？**

不说明。可能反复调用同样错误程序。需要固定评测下的调用质量、反馈利用和 rescue 等结果。

**问 4：为什么 verifier 调用了很多次测试，而 Agent 工具调用为零？**

训练器仍然需要给最终代码打分；这些测试不一定生成了模型可见 observation。

**问 5：同模型权重、同题、不同模板，输出会相同吗？**

不保证。输入 token 序列已经改变。

**问 6：有三名标注者，就一定得到真值吗？**

不保证。需要一致的原文字节、清楚的规则、独立判断和透明裁决。共同偏差仍可能存在。

**问 7：框架中的 num_turns=2 就是模型调用工具两次吗？**

不一定。框架可能把消息或其它事件计入轮数。要看实现定义和工具专用事件。

**问 8：更大的模型 tight 数更多，是否说明它更容易发生 parser bug？**

不说明。parser 规则可能始终相同且按设计运行；变化的是模型输出，调用候选数和合法性都要分开。

**问 9：没有 checkpoint，这个 run 是否完全无用？**

不是。完整日志可能支持机制计数或在线评测；但事后重评、恢复训练、验证权重变化会受限制。

**问 10：我们的非代码实验是哪一个？**

τ-bench retail。它补充交互式客服领域的证据，不等于已完成非代码规模或 RL 学习验证。

### 16.3 五道需要手算的题

**题 A。**100 题首轮通过 53；9 题后续救回；4 题首轮过但最终回退。最终过多少？

答案：53+9−4=58；final−turn1=5，不是 rescue=9。

**题 B。**合法 JSON `{"name":"add","arguments":{"a":1,"b":2}}`，只声明了 run_tests。在哪一层失败？

答案：工具名称／动作名单校验；不是 JSON 语法错误。若 parser 本身不查名称，可能先解析成功再被宿主拒绝。

**题 C。**两条臂都成功 7 题，新臂另外成功 3 题，旧臂没有独有成功。该报什么？

答案：旧7、新10，净增3，discordant pairs 为3/0，exact 双侧 p=0.25。可报告方向与效果大小，但不能宣称显著提升。

**题 D。**组内所有 reward 都是0.5，GRPO 的组内相对信号怎样？

答案：减均值后均为0，没有基于这组 reward 差异的优势；不要推导为所有正则项或全部参数更新都必定为零。

**题 E。**2×2 四格0/0/0/0.98，平均主效应是多少？

答案：各0.49；baseline 下单独更换的简单效应各0；交互对比0.98。必须说明使用的定义。

### 16.4 三个你应该亲手完成的小任务

**任务一：画路径。**不看文档，画出 serving FC、verl AgentLoop、外部反馈评测器三条路径。给每条标出 parser 在哪里、谁跑测试、谁看到反馈。

**任务二：读一条轨迹。**从已保存 JSONL 中挑一题，只读不改。写下题目身份、调用候选、工具名、参数、执行、observation、最终结果。有字段缺失就写“无法从此记录确认”。

**任务三：审核一句话。**挑论文一句强结论，写出它的证据文件、计数单位、替代解释和最小可支持措辞。能完成这个任务，比背十个模型分数更说明你掌握了项目。

## 17. 建议的学习安排与口头讲法

### 17.1 七次学习，每次完成一个产出

每次可按自己的节奏安排约 60—120 分钟。完成标准是产出，不是读完页数。

| 次序 | 内容 | 你要交给自己的产出 |
|---|---|---|
| 1 | 第1—3章，跑字符串实验 | 手写一次合法调用与三种失败形式 |
| 2 | 第4—7章，读 serving probe | 三条路径图，五个指标的分母 |
| 3 | 第8章 BFCL、Llama、τ-bench | 每个实验用“问题—改动—结果—边界”讲两分钟 |
| 4 | 第9章 RL | 手算一组 GRPO/RLOO，解释 reward 涨但工具为零 |
| 5 | 第10—11章 P3与资源 | 一张新的训练对照 run card，不启动实验 |
| 6 | 第12—15章审计与代码 | 一条原始轨迹的完整证据链，或明确指出缺失边 |
| 7 | 第16章自测与复述 | 不看稿讲五分钟，回答“你最不确定什么” |

### 17.2 用你自己的话讲三分钟

第一段讲起点：

> 我原来想研究代码模型通过测试反馈学习修复。训练后分数有数值变化，但拆成首轮和后续救回以后，改善主要出现在初稿，所以开始检查真实工具交互。

第二段讲系统：

> 工具调用不是模型直接执行函数。模型输出文本，经模板约定和解析器转换成结构化动作，执行器运行后再把反馈送回。中间某一层没接上，下游可能只看到空 tool_calls。

第三段讲最强实验：

> 在 BFCL 的指定类别上，我固定模型和题目，比较模板与 parser 的四种组合。只换一边没有从 baseline 恢复，匹配组合达到196/200首请求解析；相应两个类别的分数从0变为0.96和0.19。我们又在 τ-bench retail 观察到执行通道恢复。

第四段讲边界：

> 规模结果限于具体谱系和配置。7B 单种子训练对照已经完成，仅改变训练 parser，工具执行从 10 次增至 16,844 次，但共同程序反馈评估没有检测到收益。这个评估不直接测原生工具发起。后来我们还固定 BFCL 的原始输出做离线解析，100 条中有 92 条通过原官方 AST 评分，进一步区分生成改变和解析规则改变的作用。

这是理解后的讲述框架，不要求逐字背诵。只有你能接着解释一个原始调用和一个配对对照，这段介绍才是你自己的。

### 17.3 AI 写了很多代码，我该怎样诚实描述自己的工作

使用 AI 工具不等于没有研究工作。你仍应理解并能承担题目选择、实验设计、结果检查、统计解释和最终论文结论。

不需要声称每行代码都是自己手敲的。可以具体描述“我设计并推进了哪些对照、搭建和核验了什么流程、发现过哪些错误、怎样限制结论”。

但如果你尚不能解释哪个 parser 在训练路径里生效、reward 如何计算、分母来自哪里，就不要只背漂亮数字去面试。先完成本章的路径图和原始轨迹检查，再把工作写成简历。

你真正要达到的水平是：面对助手的新建议，能问出“这个实验改变了什么、用了哪套判据、会不会把执行恢复误当成学习”，并能据证据接受或否决建议。

## 18. 术语速查与原始资料

### 18.1 术语表

| 术语 | 在本文中的含义 |
|---|---|
| Agent | 模型策略与环境交互循环组成的系统 |
| Tool calling / FC | 提出工具名和参数，并由外部系统执行 |
| ReAct | 推理与动作交替的方法；项目采用其文本协议实现 |
| Chat template | 将消息和工具描述渲染成模型输入的规则 |
| Serialization | 将结构化信息编码成规定文本／token 格式 |
| Envelope | 标识调用边界的外层标签或标记 |
| Parser | 把输出文本／token 转为结构化调用的程序 |
| Schema | 参数与对象形状的约束 |
| Constrained decoding | 在生成过程中限制可输出的形式 |
| Serving stack | 模型推理、模板、解析等服务组件的组合 |
| Harness | 实验请求、执行、记录和评分的组织程序 |
| Executor | 实际执行工具动作的组件 |
| Observation | 返回给 Agent 的环境反馈 |
| Verifier | 检查输出是否满足评价标准的程序或机制 |
| Reward | 优化所用的数值反馈，未必等于最终成功率 |
| Rollout | 当前策略采样得到的一条交互经历 |
| Policy | 给定历史的动作／token 分布 |
| On-policy | 训练使用当前或近当前策略采样的经验；具体复用由算法决定 |
| Advantage | 样本回报相对基准的好坏 |
| GRPO | 用同 prompt 的组内结果比较估计优势的一类策略优化 |
| RLOO | 用其它采样结果构造 leave-one-out 基线的 REINFORCE 风格方法 |
| PPO | 使用概率比与裁剪等机制控制策略更新的方法 |
| KL | 衡量分布偏离的量，可进入正则／奖励 |
| Credit assignment | 判断结果应归因于哪些动作或 token |
| LoRA / PEFT | 低秩适配／参数高效微调 |
| KV cache | 自回归生成中保存历史 attention key/value 的缓存 |
| Checkpoint | 保存的模型或训练状态，内容依格式而定 |
| Rescue | 首轮失败但最后成功的任务 |
| Regression | 首轮／旧条件成功而最终／新条件失败；必须注明具体比较 |
| Ablation | 系统地改变或移除组件，研究它的作用 |
| Positive control | 预期应产生明确响应的检查条件 |
| Rescue control | 用预期能修复机制的条件排除其它解释 |
| Counterfactual control | 用对照条件检验替代解释；名称不保证已作因果隔离 |
| Confound | 与干预一起变化、可能解释结果的因素 |
| Post-treatment conditioning | 按干预影响后的变量筛选样本 |
| McNemar | 二元配对结果的方向差异检验 |
| Precision | 被判为正的样本中实际为正的比例 |
| κ / kappa | 扣除偶然一致成分后的标注一致度 |
| Provenance | 数据来自何版本、配置、过程的记录 |
| Errata | 对已报告内容的明确勘误 |

### 18.2 读原始资料的顺序

无需一次读完论文。先带着问题看对应章节：

1. [Hugging Face Chat Templates](https://huggingface.co/docs/transformers/v4.43.0/chat_templating)：看 messages 如何变成模型输入。
2. [vLLM Tool Calling](https://docs.vllm.ai/en/stable/features/tool_calling/)：看 auto、required、parser 与 strict 的区别；版本会变化。
3. [ReAct](https://arxiv.org/abs/2210.03629)：看 Thought／Action／Observation 如何交替。
4. [EvalPlus](https://arxiv.org/abs/2305.01210)：看为什么测试覆盖会改变代码能力评测。
5. [BFCL v4](https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html) 与 [τ-bench](https://github.com/sierra-research/tau-bench)：看 benchmark 自己如何定义任务和评分。
6. [DeepSeekMath](https://arxiv.org/abs/2402.03300)：先看 GRPO 的动机和组内优势，不必先重现全部数学训练。
7. [RLOO](https://arxiv.org/abs/2402.14740) 与 [PPO](https://arxiv.org/abs/1707.06347)：比较 baseline 和更新稳定化方法。
8. [verl Agent Loop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)：把框架对象映射回第6章的训练路径。
9. [LoRA](https://arxiv.org/abs/2106.09685)：理解我们为什么能用参数高效方案做7B训练。

这里链接的是公开原始工作／官方文档。它们用于学习通用机制；复现实验则必须用本项目固定的版本和产物。我们自己的论文、代码注释以及 AI 助手的解释，也都需要接受同样的证据检查。

## 19. 最新补证：固定输出、原始证据和原生 FC 评估

本章对应 2026-09-23 的实际进度。它补的是审稿人提出的三个不同问题：原输出究竟能恢复什么、别人能否检查证据、训练是否改善了自主工具使用。前两个已经有新增产物；第三个还没有推理结果。

### 19.1 为什么已有 BFCL 2×2 还值得补固定输出分析

你可以把完整服务过程拆成两个函数：生成器产生 `y = G(weights, prompt, template)`，解析器产生 `a = P(y)`。换 adapter 同时可能改变 G 和 P。因此“联合替换后评分恢复”不能直接等同于“原来的正确答案全被 parser 隐藏”。

2×2 检查组件组合的互补性；固定输出重放则先把 y 冻结，只比较对同一段文本的解释。后者排除了这次比较中新生成内容的影响，但没有证明任何宽松解析规则都适合上线。

我们冻结 documented/Hermes 臂原有的 100 条 `simple_python` 响应，不重新调用模型。新的离线规则不知道 gold answer，不改工具名、参数值或 JSON 语法，也不从多个候选里挑评分最高的一个。

| 检查层 | documented 原始响应，n=100 |
|---|---:|
| 原 serving parser 解析成功 | 0 |
| 离线 JSON 规则恢复调用 | 97 |
| 调用名称属于题目提供的工具 | 97 |
| 通过结构性参数检查 | 97 |
| 通过原官方 AST checker | 92 |

这几层回答不同问题：JSON 可解码不保证工具存在；工具存在不保证参数符合签名；结构匹配也不保证答案正确。我们的结构检查包含必需字段、类型、数组项和 enum，不包含所有 `format` 注解。最终正确性仍交给固定版本的官方 checker。

阳性对照是 repaired 臂已有结构化结果：同样重放官方 checker，复现 96/100。官方代码固定在 Gorilla commit `6ea57973c7a6097fd7c5915698c54c17c5b1b6c8`，没有修改评分规则来迎合新 extractor。

注意三个不能省掉的限定：

1. 这是**新离线提取规则**的结果，不是原 dedicated parser 的结果。原 documented 的 100 条文本都没有该部署 parser 所需的 `<tools>` 信封。
2. 92 与 96 之间的 4 题差不能直接归为“模板的因果收益”。两条生成臂不同，不能把所有差异按减法拆给某个组件。
3. 只重放 `simple_python`。多轮任务中，改动作会改变环境反馈和后续生成；不能拿旧后续轨迹冒充新动作下的反事实运行。

离线规则扫描 JSON 对象／数组，支持 name+arguments 和 function 包装，字符串形式的 arguments 必须能解码为对象；拒绝 NaN 等非标准常量。它仍不判断任意文章里的 JSON 是否真是模型要执行的动作。**离线证据工具与生产执行策略是两件事。**

### 19.2 “按文档配置”不是“官方保证 Coder 兼容”

版本化 vLLM 0.27.1 文档在 Qwen Models 下列出 `Qwen/Qwen2.5-*` 与 Hermes；这是家族层级指引，不是单独测试过 Coder 的兼容性保证。项目在 9 月 23 日回查了该版本文档，不能说当初已经保存了同样的文档快照。

具体不兼容此前已有 issue #32926。我们不应把发现该问题、发明社区 parser 当贡献。可成立的贡献是受控量化：它怎样改变第三方评分、哪些原始输出可被恢复，以及训练采样中实际获得的工具经验怎样变化。基线有可解释的选择依据，也不等于已经测出了现实部署中这种错配的普遍程度。

### 19.3 别人到底能从匿名材料验证什么

以前只有计数和 hash，别人可以检查加法，却无法判断文本是不是调用。现在本地匿名候选包增加了原始内容：

| 材料 | 能验证 | 不能据此声称 |
|---|---|---|
| BFCL 四格共 800 条首响应 | 查看生成形式、检查首响应标签 | 重建每条多轮反事实 |
| BFCL 200 条评分记录及 checker | 重算 documented 92、repaired 96 | 新规则就是部署 parser |
| τ-bench 两臂共 230 条完整任务轨迹 | 检查消息、调用、奖励与任务级统计 | 绝对分数可和官方排行榜直接比较 |
| RL 每臂 10 条确定性抽样轨迹 | 检查 extract、dispatch、执行、反馈及原文 | 代表所有 rollout 的误差率 |

RL 抽样固定在 step 1，按最小的 `(sample_index, rollout_n)` 取十条，不按成功或失败挑选。原文和 observation 保留，主机／路径／时间等元信息去除，request ID 哈希化。样本不含原训练测试输入，所以能审阅内容，不能独立重执行完整环境。extract 缺逐轮 request ID 的地方，只声称轨迹级关联，不补造精确 join。

BFCL 保留的是记录下来的推理请求字段，不是完整 HTTP 字节抓包。匿名包也仍不包含全部训练原文和重型 checkpoint。材料在本地解包复算通过，不等于已经上传公开；公开前仍要确认数据许可和匿名范围。

记住：hash 可以证明“拿到的文件是不是同一份”，不能替代“把文件给人检查”。

### 19.4 原生 FC 评估和已有评估到底差在哪里

旧共同评估：模型写代码 → 程序自动测试 → 通过 user message 给反馈。它刻意绕过训练 parser，适合比较共同反馈条件下的表现，但不要求模型主动发出工具调用。

新共同 FC 评估：模型自己发 `run_tests` 调用 → 同一个修复 parser 接受 → 执行 → tool-role 反馈。普通最终代码不触发交互反馈；对话结束后单独测试最终提交，但不把这次结果送回模型，也不算工具执行。

计划比较三组权重：共同 step-0 base、broken step 150、最终恢复路径的 repaired step 150。题目是同一批 542 题，均用相同原始模板、schema 和 repaired verl parser，不换成 BFCL 的 few-shot adapter。

这里的因果问题变成：**在同一个可用的 FC 接口下，不同训练经历是否改变主动调用、使用反馈和最终正确率？** 这是对已有 checkpoint 的事后评估，不是第二个训练 seed，也不是原预注册训练已经包含的结果。

初始冻结配置是最多四次 assistant generation、greedy、seed 0、每次最多 1024 新 token、8192 上下文预算、1200 字符 observation 上限，以及每次 generation 最多执行一个调用。上下文超限明确失败，不偷偷截断；日志保留原文、停止原因与反馈。

新 rescue 定义为首次实际工具测试失败、后续工具测试通过。首次没有调用不是“首次测试失败”，不能直接和旧协议 rescue 混池。只有指标同名还不够，事件定义也必须一致。

它也不是逐字节复刻训练：控制器每轮重渲染完整对话，held-out 测试使用 EvalPlus script mode，而训练奖励是 pytest 部分分数。tool-role 对齐减少了一个迁移差异，没有消除所有分布差异。

### 19.5 已验收什么，开 GPU 后还必须检查什么

截至本次更新，完成的是 CPU 准备：

- 两个正确 step-150 checkpoint 仍在，LoRA 张量摘要与先前审计一致；每组 392 个张量、80,740,352 个参数。
- 各导出约 155 MiB 的 LoRA adapter，逐张量回读一致，没有合并或覆盖原始模型。训练 checkpoint 还含其他状态，因此不能用 adapter 大小推断完整 checkpoint 大小。
- 真实 tokenizer 加强制工具 fixture 能形成 tool-role 回路；六项控制器测试通过；小型 CPU 模型的 PEFT 往返检查通过。
- 原生 FC runner 会检查 manifest、parser、配置、权重身份；GPU 运行显式授权，已有输出目录拒绝覆盖。

这些不证明实际 7B CUDA 推理已经能跑。下一步只是每组少量题目的 GPU 冒烟：验证载入的 LoRA 内存张量、缩放和身份，检查日志与真实推理，再测吞吐。不能用“接口返回了不同答案”代替权重核验。

当前实现是顺序 Transformers 推理，不是旧批量 vLLM。历史 1–3 GPU 小时只是预算猜测，必须根据 pilot 重估，不能当承诺。CPU 主机的 `free` 数字也可能显示宿主机资源；这次容器实际只有 2 GiB 和 0.5 CPU，要读 cgroup 限额。准备工作使用 mmap 和单线程降低开销，没有为此删除原 checkpoint。
