## 1. 先给最准确的一句话

**我们最初想用强化学习，训练一个会根据测试反馈修改 Python 代码的智能体。**

普通代码模型的工作方式是：给题目，直接写答案。我们的目标多了一层：模型写出初稿后，能够让工具测试它，读懂失败信息，再修改、再测试，最后提交答案。

最初研究的问题不是“哪个模型写代码最强”，而是：

> 只用最终测试成绩作为奖励，能不能让模型学会更有效的多轮调试，而不只是第一次写得更好？

“最终做对更多题”和“更会根据反馈修复”不是同一个结果。这一点从项目开始就很重要。

## 2. 它不是现在常见的那种仓库级编程助手

你平时用的编码助手可能会浏览目录、查找符号、修改多个文件、运行 shell、查看 Git diff，再提交修改。我们最初实现的是一个更小、更受控的系统。

| 维度 | 我们最初的实验系统 |
|---|---|
| 输入 | 一道 Python 编程题，可能包含函数签名和示例 |
| 输出 | 完整函数代码及必要的 import |
| 核心模型 | 早期主要是 Qwen2.5-Coder-1.5B-Instruct |
| 主要工具 | `run_tests(code)` |
| 工具做什么 | 把提交代码与本题预先准备的测试放到一起运行 |
| 反馈 | 通过数量、失败信息、语法错误或超时提示 |
| 多轮行为 | 基于反馈再次提交代码 |
| 最终判断 | 提交代码能否通过给定测试 |
| 不在最初范围内 | 浏览网页、读写整个用户仓库、Git 操作、部署、多工具规划 |

所以它更接近一个**测试驱动的编程题求解智能体**，而不是一个完整的软件工程师产品。

这不是缺点掩饰，而是实验设计：先把环境缩小，才能判断训练到底改变了初稿、测试行为，还是修复能力。

## 3. 为什么它仍然叫 Agent，而不是聊天模型

关键不在有没有复杂框架，而在于是否存在“动作改变环境，环境返回结果，后续决策再使用这个结果”的循环。

```text
题目 + 当前对话
      ↓
模型生成代码／工具调用
      ↓
控制程序识别动作
      ↓
执行测试 → 生成真实反馈
      ↓
反馈加入对话 → 模型继续生成
      ↓
提交最终代码，或达到轮次／长度上限
```

模型不会凭空知道运行结果。只有执行器真的运行了测试、控制程序真的把结果放回上下文，它才看得到新的证据。

你可以用熟悉的强化学习语言理解：

- **策略**：代码模型，根据历史对话生成下一段文本。
- **动作**：提交代码调用工具，或结束并给出答案。实现上动作先表现为 token。
- **环境**：题目、测试、运行代码的进程，以及负责推进对话的控制程序。
- **观测**：测试通过／失败及报错信息。
- **轨迹**：从题目到最终提交的整个生成和交互序列。
- **奖励**：最终提交在训练测试上的成绩。

不是模型说一句“测试通过了”，环境就认可。模型生成的文字与执行器返回的结果必须区分。

## 4. 用一道小题走完理想流程

下面是教学构造，不是论文实验轨迹。

题目：实现 `max_value(xs)`，返回非空整数列表的最大值。

### 4.1 模型写出一个有缺陷的初稿

```python
def max_value(xs):
    best = 0
    for x in xs:
        if x > best:
            best = x
    return best
```

正数例子可能通过，但 `[-5, -2]` 应返回 `-2`，这段代码会返回 `0`。

### 4.2 模型请求测试

逻辑上，它应发出这样的动作对象：

```json
{
  "name": "run_tests",
  "arguments": {
    "code": "def max_value(xs):\n    best = 0\n    for x in xs:\n        if x > best:\n            best = x\n    return best"
  }
}
```

注意：这是逻辑结构示例，不表示任何接口都接受裸 JSON。真正运行时还有模板约定的包装格式和 parser 规则。

模型只提供代码；本题测试由环境绑定。它不需要自己编造一份测试来给自己判分。

### 4.3 控制程序调用执行器

例如运行：

```python
assert max_value([1, 3, 2]) == 3
assert max_value([-5, -2]) == -2
assert max_value([7]) == 7
```

环境返回类似：

```text
2/3 个测试通过，1 个失败。
AssertionError: expected -2, got 0
```

### 4.4 模型读取反馈，修改代码

```python
def max_value(xs):
    best = xs[0]
    for x in xs[1:]:
        if x > best:
            best = x
    return best
```

再测试，通过，提交答案。

我们希望训练提高的是这种行为出现的概率：**理解负数边界条件，针对反馈修正初始化，而不是随便重写一遍。** 但仅观察到它改了代码，还不能证明它使用了反馈；需要看修改内容和结果，必要时设计反馈对照。

## 5. 系统里每一块分别负责什么

### 5.1 模型：提出方案，不负责真正执行

Qwen2.5-Coder 本来就具备一定 Python 生成能力。项目不是从零教它 Python，而是希望 RL 在已有能力上调整行为：更好的初稿、合适的测试动作、有效的修改。

模型输出的是 token，不会直接启动 Python 进程。生成“调用工具”的文本，只是动作请求。

### 5.2 Chat template 和 parser：把对话和动作接起来

chat template 把 system、user、assistant、工具说明等结构化信息拼成模型输入。parser 则从生成文本中提取工具名称和参数。

这个接口承担双向约定：模型得知道工具是什么，输出格式也得能被控制程序理解。后来论文研究的正是这里可能出现的错配。

还要区分两条路径：独立 serving probe 通过 vLLM 的服务端 parser 读取调用；verl 训练 AgentLoop 有自己的 parser registry。**不能把训练中所有解析都描述成 OpenAI API 服务端在做。**

### 5.3 AgentLoop：决定下一步该做什么

AgentLoop 是控制程序，不是另一个聪明的模型。它大致负责：

1. 取出当前样本和对话。
2. 请求模型生成。
3. 检查是否有可接受的工具调用。
4. 有调用则执行，并把反馈加到历史里。
5. 根据结束条件决定继续生成还是结束轨迹。

FC 路径利用框架的工具循环；后来另写了 ReAct 循环。具体样本里的 `agent_name`、实际加载的配置以及版本会决定走哪条路，不是脚本里写一个名字就一定生效。

### 5.4 CodeTool：给每道题管理测试状态

[code_tool.py](../code_tool.py) 实现 verl 的工具适配层，主要生命周期是：

- `create`：创建这条轨迹的工具实例，把本题测试绑定进去。
- `execute`：接收 `code`，调用执行器，返回测试反馈。
- `release`：清理实例状态，避免长训练不断累积内存。

工具状态包含测试内容、调用次数、最近通过比例等。不同题有自己的测试，不是所有题共用一个判定函数。

### 5.5 Sandbox：运行代码并收集结果

[sandbox.py](../sandbox.py) 负责临时目录、子进程、运行时间和资源限制，以及测试结果的解析。工具配置中能看到 10 秒 timeout、512 MiB 内存限制和 1200 字符反馈上限；这些是配置示例，具体实验以冻结配置为准。

这里的 sandbox **不是能安全执行任意恶意代码的强隔离容器**。资源限制和临时目录不等于完整权限、网络或文件系统隔离。项目中的可疑代码检测也主要用于记录，不是安全认证。

### 5.6 verl、Ray、vLLM：让训练和生成运行起来

- **verl**：组织轨迹采样、奖励、优势估计与参数更新。
- **Ray**：组织不同进程和 worker；工具与训练日志可能分布在不同进程。
- **vLLM**：在训练 rollout 中承担高效生成等工作；它不是算法题的正确性判定器。

这些是基础设施，不是我们发明的算法。项目工作是在这些基础设施上搭建工具环境、反馈与评测，并检查各层是否真的接通。

## 6. 最值得你掌握的设计：测试有两条路径

表面上两条路径都调用了运行代码的函数，但意义完全不同。

| | 交互测试 | 最终奖励测试 |
|---|---|---|
| 什么时候发生 | 轨迹中，工具调用被接受后 | 轨迹生成结束后 |
| 谁触发 | AgentLoop 调度工具 | 训练奖励函数 |
| 代码来源 | 工具参数里的代码 | 从轨迹中提取的最终提交 |
| 结果给谁 | 返回模型上下文 | 返回训练算法 |
| 模型能否据此继续改代码 | 如果还有预算，可以 | 这条轨迹已经结束，不能 |

对应源码入口是 [CodeTool.execute](../code_tool.py) 与 [reward_code.compute_score](../reward_code.py)。

### 为什么 reward 能涨，工具却没执行？

假设模型直接输出最终 Python 代码，没有任何被接受的工具调用：

```text
题目 → 模型直接写代码 → 轨迹结束
                         ↓
                 奖励函数提取代码
                         ↓
                   测试并得到分数
                         ↓
                     更新模型
```

这仍然可以训练出更好的单轮代码，却没有发生“模型看到测试失败后再修改”的过程。

因此：

> sandbox 被调用过，不等于工具交互发生过；reward 非零，不等于模型收到过工具反馈。

后来我们给 `CodeTool` 和奖励路径分别计数，就是为了消除这个歧义。

### 为什么不能只看 `CodeTool.calc_reward`？

工具类保留了这个方法，但项目的奖励入口是单独配置的 `custom_reward_function`。仓库记录指出，在所用 verl 路径中不能指望工具的 `calc_reward` 自动被调用。因此理解代码时要追实际调用链，而不是看到一个叫 reward 的方法就认定它决定了训练奖励。

## 7. 奖励为什么用通过比例，而不是“调用一次就加分”

最初采用的思路是 **outcome-only + partial credit**：只根据最终代码的测试成绩给奖励，允许部分通过获得部分分数。

教学例子：十个测试，通过七个，则奖励为 0.7；一个都没运行成功，不应获得免费满分。当前验证器还把 skipped、xfailed、xpassed 纳入分母，避免跳过测试抬高成绩；这是后来的修复，不能反推最早版本已具备。

为什么不奖励“多调用一次工具”？因为那可能训练出为了拿分而反复调用的行为。我们想研究最终成绩信号是否能自然强化有效调试，不想事先把“调用越多越好”写进奖励。

为什么不只给全对 1、否则 0？对小模型和难题，一组候选可能全是 0，缺少区分信号。部分分数更容易区分候选，但也引入 verifier 可靠性问题。

通过测试也不等于程序对所有输入正确。模型可能只覆盖了当前测试，测试本身也可能有缺陷；所以需要更强的 held-out 评估和数据检查。

## 8. RL 是怎么训练这个 Agent 的

早期主线是 1.5B 模型、GRPO 两个 seed 和 RLOO 一个 seed，各 150 步。历史配置每步 16 道题、每题采样 8 条轨迹，即约 128 条轨迹。

注意这里的三个“次数”：

- 150 个 training steps 是参数更新过程的步数。
- 每题 8 条 rollout 是同一题的不同候选轨迹。
- 每条轨迹内部还可能包含多次生成与工具测试。

八条 rollout 不是一条轨迹里修八次；150 步也不是对一道题写 150 版答案。

以 GRPO 的直觉为例，同一道题采到几个候选，奖励分别为 0、0.3、0.8、1。算法会比较组内相对表现，结合概率比、裁剪及 KL 等约束更新模型，使相对高奖励行为更容易出现。这不是简单地把正确代码复制进去再做一次普通监督学习。

有一个重要限制：即使高分轨迹用了工具，最终奖励也没有逐步告诉模型“这一次调用有用、那一次修改没用”。信用分配、探索和采样仍然决定它实际学到什么。**我们希望它学调试，不代表奖励设计保证它学调试。**

另外，一道题的推理过程中通常不更新权重。模型根据反馈改代码，首先是上下文条件变化；累计轨迹经过训练更新后，才是参数学习。

## 9. 训练数据和评估任务怎么分工

训练侧来自 KodCode，题目绑定测试。项目做了与评估集的重合检查，也检查参考答案能否通过本题测试。

历史记录中的 7,669 是去污染后数据池口径，不应随口说成每次训练实际用了 7,669 条。当前数据准备脚本还能从池中抽取 train/val 子集，默认数量也不代表所有历史 run 的真实样本量；复现时以当次 parquet 和 manifest 为准。

测试内容在准备数据时进入两个位置：

1. 工具实例参数：交互时用它测试代码并反馈。
2. 奖励的 ground truth 字段：最终打分时再用它。

模型看到的 prompt 不等于包含完整测试源码。把测试交给环境与把答案直接放进 prompt 是两回事。

评估侧使用 EvalPlus 相关保留任务，还拆成两种问题：

- **从零做题的多轮通道**：先写初稿，再允许反馈和修改，分解首轮与最后成绩。
- **固定错误代码的修复通道**：不同 checkpoint 收到同样的错误初稿和报错，更直接比较修复表现。

固定错误初稿很重要：如果每个模型只修它自己写错的题，强模型和弱模型面对的失败集合不同，不能直接比较修复率。

历史清洗后多轮分母常见 540，后来正式 7B 使用冻结的 542 题 manifest。它们有版本和纳入规则差异，不是想用哪个分母就用哪个；也不能把通道内题数误写成原始 benchmark 的标准总题数。

## 10. 最初怎么判断“真的学会了多轮修复”

至少要把三个数字分开：

1. **首轮通过**：没有这轮反馈帮助，初稿就对了多少题。
2. **最终通过**：经过允许的交互后，最终做对多少题。
3. **后续救回**：初稿没通过，后来通过的题有多少。

举例，训练前首轮过 60 题、最终过 65 题；训练后首轮过 70 题、最终过 75 题。总分提高十题，但后续救回仍是五题。它与“初稿改善”的解释相容，不能直接拿十题增益证明多轮调试学好了。

真实项目的早期三次训练，最终 pass 的数值增益约 2.6–2.8 个百分点，对应 p=0.064/0.078/0.077，未达到通常的 0.05 阈值。增益分解主要落在首轮；完整历史 checkpoint 的后续救回范围是 5–10/540。

这些现象促使我们查工具链。它们本身不证明“小模型永远学不会”，也不证明“原因肯定只有 parser”。尤其早期 1.5B 探针还有工具名不正确等语义问题，不能把所有零执行都归因于有效调用被遮蔽。

## 11. FC 和 ReAct 在项目历史里是什么关系

它们是实现工具交互的不同协议，不是两个完全不同的产品。

- **FC**：通过工具 schema 告知模型工具，模型生成调用形式，由对应 parser 提取。
- **ReAct 文本协议**：提示模型按 `Thought / Action / Action Input` 等形式工作，由自定义控制逻辑提取动作。

后来写的 [react_agent_loop.py](../react_agent_loop.py) 是为了让文本动作进入真实测试回路，并做对照。ReAct 仍依赖模型遵循约定和解析逻辑，不能理解成“完全不需要 parser”或“天然更聪明”。

当前 [prepare_code_data.py](../prepare_code_data.py) 默认写入 `react_agent`，保存的部分训练脚本也已有后来的 ReAct 设置。这正说明不能拿今天的默认脚本代表最初 FC run：数据中的 agent 名称也会决定实际执行路径。

## 12. 最初的工程工作具体落在哪里

如果有人问“除了调用现成模型，你们做了什么”，可以沿着这条调用链回答，而不是笼统说搭了一个 Agent。

| 工程部分 | 解决的问题 | 源码入口 |
|---|---|---|
| 数据准备 | 给题目绑定测试、分开工具输入与奖励输入 | [prepare_code_data.py](../prepare_code_data.py) |
| 工具 schema 和生命周期 | 让框架能创建、执行、释放本题工具实例 | [code_tool.py](../code_tool.py)、[配置](../code_tool_config.yaml) |
| 代码与反馈处理 | 从输出提取代码，把执行结果压成可读反馈 | [code_tool_core.py](../code_tool_core.py) |
| 测试运行 | 子进程运行、限时限资源、结果判定 | [sandbox.py](../sandbox.py) |
| 奖励接线 | 从最终提交计算测试通过比例 | [reward_code.py](../reward_code.py) |
| 训练入口 | 挂接评估，再进入 verl 训练 | [launch_ppo.py](../launch_ppo.py) |

这些模块共同构成实验系统。没有 UI，不代表没有 Agent；有工具类，也不代表工具真的在训练里执行了。后者必须用轨迹和独立计数证明。

源码注释也会过时。例如“模型学会某格式”“因此必须走某协议”等判断不能只靠注释引用，必须回到对应实验与实际产物。

## 13. 后来为什么变成了接口测量论文

原来问的是：怎样训练出更会调试的代码模型？

为了回答，我们先要确认训练实际产生了什么经验。结果发现，“开了 multi-turn”“给了工具 schema”“reward 在提高”都不足以证明工具回路接通。这使研究问题往前移了一层：

> 在判断模型会不会使用工具以前，我们是否准确观测到了模型输出，以及这些输出是否真的变成了环境动作？

于是才有后来的 parser、template、模型规模、BFCL 和 τ-bench 对照。它们不是最初 code agent 的全部功能，而是为诊断、量化这个问题补充的实验。

后来正式 7B 单 seed、150 步 LoRA 对照把问题做得更干净：只改变训练 parser，工具执行从 10 次增至 16,844 次；但共同程序反馈评估没有检测到成功率或 rescue 改善。这证明训练经验可以被接口大幅改变，不证明更好的原生工具策略一定学到或一定没学到。

现在准备的共同原生 FC 评估则重新贴近最初目标：让 base、broken、repaired 在同一个可用接口下，自己决定是否测代码、如何用反馈。24 题 pilot 已通过工程验收，完整 542 题对比仍未完成；不能把 pilot 写成最终学习结论。

## 14. 你可以怎么用自己的话讲这个最初的项目

> 我最初做的是一个面向 Python 编程题的单工具代码智能体。模型先写代码，通过 run_tests 拿到真实测试反馈，再决定怎么改；我希望用 verl 的强化学习训练，让它不只是初稿更好，也更会根据反馈修复。系统包括测试工具、执行环境、最终奖励和分解评估。后来发现，训练分数变化不代表工具交互真的发生，所以开始逐层检查模型输出如何变成工具动作，项目才进一步发展成接口测量研究。

如果接着问“你们做的是 Copilot 或 SWE-agent 吗”，可以回答：

> 不是完整的仓库级软件工程助手。我们把场景收敛到函数级编程题和一个测试工具，方便控制反馈与奖励，研究多轮修复和工具接口的作用。

如果问“你们的创新是 GRPO 吗”，可以回答：

> 不是。GRPO、verl 和基础模型都是已有工作；项目重点是代码工具环境、受控评估，以及对接口如何影响可观测行为和训练经验的实证分析。

## 15. 读完后用这六题检查自己

1. **模型输出“我已经测试过”算工具调用吗？** 不算，要有真实解析、执行和反馈记录。
2. **测试函数被调用一万次，等于有一万次交互吗？** 不等于，可能包含最终奖励或终端评分。
3. **模型根据报错改了代码，权重变了吗？** 这次对话内未必；推理时使用上下文与训练更新参数不同。
4. **八条 rollout 是修八遍吗？** 不是，是同题八条采样轨迹，每条内部另有轮次预算。
5. **总分提高就证明学会调试了吗？** 不证明，要拆开初稿、后续救回及实际工具行为。
6. **原生 FC 评估为什么还值得做？** 因为旧评估主动提供反馈，而最初目标还包含模型自己发起工具动作。

建议你先亲手画出第 6 节的两条测试路径，再追 `CodeTool.execute` 和 `reward_code.compute_score`。能解释清楚“反馈给模型”和“分数给训练器”的区别，就已经掌握了这个项目最重要的一半。
