## 第 0 章 · 先补背景:这个项目里的每个词是什么意思

如果你对 agent 这块不熟,下面五个概念决定了后面能不能读懂。建议先读完这一章。

### 0.1 什么是 "code agent"

普通的 LLM 用法是:给它题目,它一次性输出代码,结束。**单轮。**

code agent 的用法是:给它题目,它写代码 → **调用一个工具去跑测试** → 拿到报错 →
改代码 → 再跑 → 直到通过。**多轮。**

这个"跑测试"的动作,就是 **tool call(工具调用)**。整个项目围绕它展开。

### 0.2 工具调用在技术上是怎么发生的

这是最关键的一节。工具调用**不是**模型直接执行了什么,而是一条流水线:

```
① 模型在输出里写一段特殊格式的文本，表示"我想调用 run_tests，参数是这段代码"
        ↓
② 推理服务端（本项目用 vLLM）用一个 parser 去解析这段文本
        ↓
③ 解析成功 → 服务端在 API 返回里填 tool_calls 字段
   解析失败 → tool_calls 是空数组 []
        ↓
④ 你的程序看到 tool_calls 非空 → 真的去执行那段代码 → 得到测试结果
        ↓
⑤ 把结果作为新的一轮消息（Observation）喂回给模型 → 模型进入第二轮
```

**注意 ②。** 模型写的文本必须**恰好符合 parser 期待的格式**,parser 才认。
格式不对,parser 就当没看见,`tool_calls` 返回空数组,而 **HTTP 状态码仍然是 200**。

下游看到的是:`tool_calls: []`。这和"模型压根不想调用工具"**一模一样**。

> **这就是整篇论文的题眼。** 后面所有实验都在拆解这一步。

### 0.3 两种协议:FC 与 ReAct

同一件事有两种做法:

**FC(Function Calling,函数调用)** —— "官方"做法。
你把工具的 JSON schema 通过 API 的 `tools` 参数传给服务端,服务端把它渲染进 prompt,
模型输出特殊标记(如 Qwen 系的 `<tool_call>...</tool_call>`),服务端 parser 解析。
优点是结构化;缺点是**依赖模型被训练过输出那个特定标记**。

**ReAct(Reasoning + Acting)** —— "土"做法,2023 年那篇经典论文。
你在 system prompt 里用自然语言告诉模型:

```
Thought: <你的思路>
Action: run_tests
Action Input: <你的代码>
```

然后你**自己写正则**去解析模型的输出。不依赖服务端 parser,不依赖模型被专门训练过。

**本项目最核心的对比,就是这两者。** 而结论是:很多时候 FC 输 ReAct,不是因为协议本身,
**而是因为 FC 那条链路上有一个静默失效的 parser。**

### 0.4 什么是 RL 训练一个 agent

**RL(强化学习)** 在这里的意思是:让模型自己做题,做对了给正奖励,做错了给负奖励,
用这个信号去更新模型参数。

具体用的算法是 **GRPO** 和 **RLOO**——细节可以先不管,你只需要知道它们的共同点:

> **模型只能从"自己实际产生过的轨迹"里学习。**

这个性质后面会变成整篇论文最狠的一击。如果工具调用从来没有成功执行过,
那么"调用工具 → 拿到报错 → 修好 → 得高分"这条轨迹**从未出现在训练数据里**,
RL 就没有任何东西可以强化。

一次训练的循环叫一个 **step(步)**。每一步:

```
rollout（模型生成一批轨迹） → 打分 → 算梯度 → 更新参数
```

本项目的配置:`batch 16 × rollout.n 8 = 每步 128 条轨迹`,跑 150 步。

### 0.5 评测集:EvalPlus / HumanEval+ / MBPP+

**HumanEval** 和 **MBPP** 是两个经典的 Python 编程题库。**EvalPlus** 是它们的加强版
——原版测试用例太少,很多错代码也能蒙混过关,EvalPlus 补了大量测试用例。

本项目用:HumanEval+ 319 题 + MBPP+ 677 题。扣掉 2 条已知有缺陷的题,
**分母是 540(multi 通道)和 454(repair 通道)**。

**pass@1** = 生成一次,通过的比例。

## 第 1 章 · 起点:一条说不通的训练曲线

### 1.1 原本想做什么

最初的目标很朴素:**用 RL 训练一个会多轮调试的 code agent。**

配置:

| 项 | 值 |
|---|---|
| 被训模型 | Qwen2.5-Coder-1.5B |
| 框架 | verl 0.9.0 |
| 算法 | GRPO ×2 seed + RLOO ×1 seed |
| 每步轨迹 | batch 16 × rollout.n 8 = 128 |
| 训练步数 | 150 |
| 训练数据 | KodCode(去污染后 7669 条) |
| 评测 | EvalPlus 保留集 |
| 硬件 | 单卡 A800 80G |

### 1.2 结果:数字在涨,但涨的地方不对

| run | multi 最终 | turn-1 | repair |
|---|---|---|---|
| GRPO seed42 | 64.8% → 67.6% (p=0.064) | +2.6% (p=0.093) | +4.6% (**p=0.030**) |
| GRPO seed1 | 64.3% → 67.0% (p=0.078) | +3.0% (p=0.053) | +3.7% (p=0.097) |
| RLOO seed42 | 64.6% → 67.2% (p=0.077) | +2.6% (p=0.082) | +0.9% (p=0.786) |

三个独立 run 方向一致、幅度都是 +2.6~2.8%。**但 p 值在 0.06–0.08,按 0.05 都不显著。**

> **知识点:为什么三个不显著的 run 反而比一个显著的 run 可信?**
> 单次实验的 p<0.05 可能是运气。三次独立实验(两种算法 × 两个 seed)方向一致、
> 幅度接近,这种一致性本身是证据。论文里的写法是:
> "可信度来自方向与幅度的一致,而非任何单次检验。"
> **不要把 p=0.064 写成 "marginally significant" 蒙混过去。**

### 1.3 真正的异常在分解里

把"新通过的题"拆开看:

- **91–94% 是第一轮就通过的**
- 靠第 2 轮及以后救回的题数:从 step 0 到 step 150 一直是 **6–9 / 540**,横盘

也就是说:**RL 提升了初稿质量,多轮调试能力完全没有变化。**

这就是整个项目的起点问题:**多轮为什么不动?**

自然的解释是"1.5B 太小,学不会多轮修复"。**这个解释是错的**,但要证明它错,
花了后面所有的篇幅。

## 第 2 章 · 第一次排查:跨家族实验,以及一场彻底翻车

### 2.1 思路

如果 1.5B 学不会,那大一点的模型总会吧?于是设计了**跨家族探针实验**:

不训练,只测。拿现成的模型,在同一批题上分别用 ReAct 和 FC 跑一遍,看:

- **L1(发起率)**:模型有没有试图调用工具
- **L2(解析)**:服务端有没有解析出来
- **L3(通过率)**:首轮通过 / 最终通过

题集:KodCode 去污染池的 `clean[:100]`,**所有实验共用同一批 100 题**
(这一点后来被反复验证:49 个正式臂,唯一集合数 = 1)。

> **知识点:为什么必须共用同一批题?**
> 因为要做**配对检验(McNemar)**。配对检验比独立检验强得多:
> 它只看"同一道题在 A 下过、在 B 下不过"的条目数(记作 b 和 c),
> 消掉了题目难度这个巨大的干扰源。100 题配对的功效,远高于 100 题非配对。

### 2.2 第一版结果看起来非常漂亮

Llama-3.1-8B:ReAct 81% vs FC 50%,McNemar b/c = 38/7,**p = 3.1e-06**。

**p 值小到六个零。** 当时的感觉是"实锤了,ReAct 完胜 FC"。

### 2.3 然后复盘发现:两张表全都不能用

这是整个项目最重要的一次翻车,记录在 `fixes/AUDIT.md`。八个洞:

---

**洞 1(最严重):26 条空代码撑起了全部显著性**

剔掉 FC 首轮代码为空的 26 条后:

| | n | ReAct | FC | b/c | p |
|---|---|---|---|---|---|
| 全部题目 | 100 | 81% | 50% | 38/7 | 3.1e-06 |
| 剔除空代码 26 条 | 74 | 81% | **68%** | 17/7 | **0.064** |

**剔掉就不显著了。** 而且这 26 条**无法归因**,因为代码里写着:

```python
except Exception:
    code = ""
```

JSON 解析失败、key 名不对、模型真的给了空——**三种完全不同的原因被压成同一个空串**,
而且原始 `arguments` 没保存。

> **教训一:永远不要用一个 `except: pass` 把不同的失败原因抹平。**
> 出错时至少要记下原始输入。这一个 `except` 让 26 条数据彻底作废。

---

**洞 2:max_tokens 系统性偏袒某一方**

`gen()` 和 `gen_fc()` 都写 `max_tokens=1024`,看起来公平。**实则不然**:

FC 把代码放进 JSON 字符串,所有换行要转义成 `\n`,**同一份代码在 FC 下更费 token**。
共用上限时 FC 更容易被截断 → 截断的 tool_call 是残缺 JSON → 解析失败 → 空代码 → 计为失败。

这正好是洞 1 那 26 条最可能的成因。而 `finish_reason`(告诉你是正常结束还是被截断)
**当时被丢弃了**,所以这个假设用现有数据无法证伪。

> **教训二:公平不等于相同的参数值。** 两个协议的 token 效率不同,给同样的上限就是不公平。

---

**洞 3:比率的分子是轮数,分母是题数**

```python
parse_modes[parse_mode] += 1     # 每一轮都累加
...
print(parse_modes[k] / n)        # 却除以题数
```

多轮模型被系统性抬高,理论上可以超过 100%:

| 模型 | 脚本报的"直接给代码率" | 逐题实际 |
|---|---|---|
| Mistral-7B react | 67% | **54%** |
| DS-6.7B react | 59% | 59%(恰好单轮,没暴露) |

**DS-6.7B 恰好是单轮,所以数字正确——这个 bug 差点永远藏着。**

---

**洞 4:引用了脚本自己判定为不可用的数据**

日志里明明写着:

```
请求错误: 3   ⚠️ 非零，本组结果不可用
```

脚本正确打了警告,**但返回码仍是 0**,于是这组数据照样被填进对比表。

修复:`n_err > 0` 时以**退出码 2** 结束,让调用方无法静默忽略。

> **教训三:警告没有强制力。** 要让错误状态**必须**被处理,就得让它变成非零退出码或异常。

---

**洞 5:不同家族用了不同的判定口径**

`parser_adapter()` 对 Qwen 用 `legacy`(严格要求 Action/Final Answer 格式),
对其他家族用 `cross_family`(允许直接给代码块也算有效作答)。

于是**同一个行为在 Qwen 上记为失败、在 Llama 上记为成功**,跨家族通过率不可比。

---

**洞 6:轨迹缺 provenance(来源记录)**

只存了 `protocol` / `strength`,没存 `adapter`、`sys_file`、`max_tokens`。
消融实验的 B 臂和 C 臂**除了文件名以外无法区分**。

> **教训四:每条数据都要带着"我是怎么产生的"一起落盘。**
> 后来 provenance 字段扩到 `model / protocol / adapter / max_tokens / clean_index / seed / temperature / fc_schema`。

---

**洞 7:取样不是随机**

`idxs = clean[:a.n]` —— 取前 100 条,不是随机抽的。

配对因此成立(好事),但对题库不具代表性。**决定暂不改动**——改了会切断与全部历史数据的
可比性。定案后另做一次固定随机种子的复制实验(即后来的 P0,至今未跑)。

> **教训五:有些坑要认下来写进 Limitations,而不是立刻修。**
> 修它的代价是丢掉所有历史可比性。

---

**洞 8:运维**

DS-1.3B 本地只有 93/100 行——关机守护脚本"满 100 行立即杀队列关机",
而同步循环 45 秒一轮,卡在最后一次同步之后就断电了。

> **教训六:自动关机要先 `sync` 再留缓冲。**

---

### 2.4 这次翻车的元教训

八个洞里,**只有洞 4 是脚本主动报出来的**,其余七个都是复盘时人工翻代码找出来的。

而更要命的是后来发现:**洞 2 的"修复"当时根本没生效,而且方向判反了。**

`fix_audit.py` 只替换了 `gen_fc()` 里的字面量 `1024`,而 ReAct 侧的 `gen()` 用的是
**函数默认参数** `max_tokens=1024`,没被匹配到。落盘的 provenance 却统一写 `MAX_TOKENS`。

结果:**ReAct 实跑 1024、FC 实跑 2048,而两者都记录成 2048。**
真实情况与最初判断**相反**——获得更长预算的是 FC。

发现后以真实 2048 重跑三个主 ReAct 臂(v14):Llama 80→**80**、Qwen 74→**74**、
Mistral 32→**33**。**实证影响为零**(这些编程题的 ReAct 响应中位长度约 1000 token)。

> **教训七(全项目最重要的一条):声称修好而未验证生效,比不修更危险。**
> 它同时污染了数据**和对数据的信任**。此后所有修复都以外部验证器核对,
> 不采信"补丁已应用"这一步。
>
> 受影响的 7 个臂全部列进了 `ERRATA.md`,没有一条被悄悄吸收。

## 第 3 章 · 重跑:四个家族,四个失败层

修完八个洞、显式统一所有口径后重跑(`run_v3.sh`)。这次得到了论文的第一根骨架。

### 3.1 四个家族在四个不同的层失败

| 家族 | 失败层 | 表现 | 能否提前检测 | 补救 |
|---|---|---|---|---|
| DeepSeek-Coder | **模板层** | chat template 根本不注入 tools | ✓ 检查模板即可 | 无 |
| Qwen2.5-Coder | **parser 层** | 输出 ```json 而非 `<tool_call>` | ✗ 模板检查会假阳性 | 专用适配器 0→84 |
| Llama-3.1-8B | **schema 层** | 23% 把**题目函数本身**当工具调用 | ✗ 必须查参数内容 | `strict: true` 23→0 |
| Mistral-7B | **词元层** | 重复吐 `[TOOL_CALLS]` 触发 400 | ~ 有时报错 | 四种配置全失败 |

**关键性质:只有缺 `--enable-auto-tool-choice` 会硬报错,其余全部静默降级。**

### 3.2 一个假阳性检查:模板里有 tools ≠ 模型会用 tools

判断一个模型支不支持 FC,常见做法是检查 `apply_chat_template(tools=...)` 有没有把
schema 渲染进 prompt。这个检查:

- 对 DeepSeek-Coder **正确判为不支持**(模板确实不注入)
- 对 Qwen2.5-Coder **给出假阳性**

原因:Qwen2.5-Coder 的 `tokenizer_config.json` 从 Qwen2.5-**Instruct** 继承了
Hermes 工具脚手架,所以模板检查返回 True。**但这个变体从未在 tool call token 上训练过。**

> **模板是继承来的,训练不是。**
> **协议支持是逐 checkpoint 的属性,无法从 chat template 推断。**

### 3.3 Mistral 的特殊性:它没有一个可用的 FC 臂

四种配置全试了,**每一种都产生请求错误**:

| 配置 | 错误条数 |
|---|---|
| 仅 `--tool-call-parser mistral` | 2 |
| 官方模板(`tool_chat_template_mistral_parallel.jinja` + hf 三参数) | **42** |
| parser + `strict: true` | 3 |
| 官方模板 + `strict: true` | **39** |

**vLLM 官方推荐的那个配置,错误率从 2% 升到 42%。**

含缺失数据的臂**不算通过率、不算 p 值**。所以正确的表述不是"Mistral 上两协议无差别",
而是:**Mistral 在 FC 下无法产出一份无错误的 100 题数据。**

(早期版本曾在这种臂上照算 p=0.648,该数值已作废,写进 ERRATA。)

## 第 4 章 · Llama 的四重对照:第四重推翻了前三重

这一章是整篇论文方法论上最值得学的部分。

### 4.1 观察

Llama-3.1-8B 在 FC 下,**23% 的题里把题目要求实现的那个函数当成工具去调用**,
参数填的是那个函数的形参:

```json
{"name": "can_form_word", "arguments": {"tiles": [...], "word": "..."}}
```

而合法工具只有 `run_tests`。看起来像模型的"角色混淆"。

### 4.2 三个单变量对照,逐一排除替代解释

| 替代解释 | 对照实验 | 空参数率 | 结论 |
|---|---|---|---|
| schema 参数没写描述 | rich vs terse | 23 → 22(p=1.000) | 排除 |
| ReAct 只是多了思考步骤 | FC + Thought 脚手架 | 23 → **59**(p<0.001,**反向恶化**) | 排除 |
| 服务端没按官方推荐配置 | + 官方 chat template | 23 → 22(p=0.125) | 排除 |

rich 版的工具描述里明明白白写着:"这个工具不是你要实现的那个函数,不要把题目函数的
参数传进来",还给了 `"def add(a, b):\n    return a + b"` 作为例子。
**在这样的显式警告下,仍有 22/100 填错,且错的是同一批参数名。**

第二行特别有意思:把 ReAct 的 Thought 步骤搬到 FC 上,**差距不但没缩小,反而从 31 点
扩大到 56 点**,schema 混淆从 23% 升到 59%。

> **机制:** Thought 要求模型先分析题目函数的签名、参数、边界情况。
> 带着这个语境去构造工具调用时,它把刚推理过的那些形参直接填进了工具的 arguments。
> **对一个角色定义模糊的接口,加强推理会放大误用,而不是纠正它。**

三重否定做完,当时的结论是:**这是模型的能力缺陷。**

### 4.3 第四重对照:结论作废

回头再读 vLLM 文档,有一句话:

> `tool_choice="auto"` 下要施加 schema 级约束,需要 `VLLM_ENFORCE_STRICT_TOOL_CALLING=true`
> (默认已开)**且至少一个工具带 `strict: true`**;否则 vLLM 从纯文本抽取调用,
> "arguments may occasionally be malformed or **violate the function's parameter schema**"。

**上面所有臂都没带 `strict: true`。** 补上之后:

| 臂 | 发起 | 空参数 | 首轮通过 | 最终通过 |
|---|---|---|---|---|
| ReAct | 98 | 0 | 61 | **80** |
| FC terse(仅 parser) | 97 | 23 | 34 | 49 |
| FC 官方模板 | 95 | 22 | 33 | 44 |
| **FC 官方模板 + `strict:true`** | 98 | **0** | 46 | **61** |

McNemar:**b=18, c=1, p=0.0001。** 函数名 98/98 全对,错填参数名 0 条。

**那 22% 不是模型的角色混淆,是缺 `strict: true` 的配置伪影**——正是 vLLM 文档
字面描述的情形。5a–5c 三重否定全部没覆盖到真正的原因,其"这是模型问题"的结论**作废**。

### 4.4 但协议差距没有消失

ReAct 80 vs 完整配置的 FC 61,McNemar b=27 c=8,**p=0.0019**。
差距从 31 点缩到 19 点,**仍然显著**。

### 4.5 这一节自己就是论点的例证

> 本工作带着明确怀疑、连做三个单变量配对对照,仍然把一个配置问题写成了
> "模型能力缺陷",直到第四个对照才发现。
>
> **"工具接口错配伪装成模型缺乏智能体能力"——这一机制的受害者包括本工作自身。**

这段被写进了论文正文。**主动交出自己的失败,比宣称自己严谨更有说服力。**

> **教训八:排除了三个替代解释,不等于找到了真原因。**
> 单变量对照只能否定,不能肯定。要肯定,必须直接干预你认为的那个变量并看到它翻转。

### 4.6 主表:统一配置之后的三组对比

把每个家族**最好的那个配置**拿出来放一起,全部真实 `max_tokens=2048`、同一 100 题、
`temperature=0`:

| 模型 | ReAct 首轮 | ReAct 最终 | FC 首轮 | FC 最终 | b/c | p | FC 臂 |
|---|---|---|---|---|---|---|---|
| Llama-3.1-8B | 61 | **80** | 46 | 61 | 27/8 | **0.0019** | 官方模板 + strict |
| Qwen2.5-Coder-7B | 57 | **74** | 53 | 62 | 17/5 | **0.0169** | 专用适配器 |
| Mistral-7B-v0.3 | 26 | 33 | **N/A** | **N/A** | **N/A** | **N/A** | 无可用臂 |

**接口修好之后,协议差距依然存在,而且两个家族方向一致。**

但还有一个必须做的分解:ReAct 解析 95/100 而适配器只有 84/100,
那 74-vs-62 里有多少只是"FC 有 11 题根本没机会尝试"?

只看**两个协议都成功解析**的题:

| 家族 | 两边都解析的题数 | ReAct | FC | b/c | p |
|---|---|---|---|---|---|
| Qwen2.5-Coder-7B | 83 | 63 | 56 | 11/4 | 0.118 |
| Llama-3.1-8B | 96 | 78 | 60 | 25/7 | **0.0021** |

**答案因家族而异,论文就照这样报。** Llama 上协议差距无歧义;
Qwen 上在这个样本量下**没有检测到**残差——注意措辞,这不等于"没有残差"
(见第 10.3 节那个 [-0.5, +17.4] 的置信区间)。

**所以论文的说法是:残差协议效应在一个家族上成立,在另一个家族上未定。**

## 第 5 章 · 规模曲线:模型越大,被吞掉的越多

### 5.1 实验

Qwen2.5-Coder,`tool_choice=auto`,hermes parser(vLLM 文档对 Qwen2.5 的推荐配置),
1.5B → 32B 共 21 倍规模,每档 100 题:

| 规模 | 服务端解析出 | 模型实际产出的合格调用(tight) |
|---|---|---|
| 1.5B | 0 | 0 |
| 3B | 0 | 4 |
| 7B | 0 | 21 |
| 14B | 0 | 36 |
| **32B** | **0** | **80** |

**服务端在每一档都报 0,而模型实际写出的合格调用一路涨到 80/100。**

"合格调用"的判据很严:`{"name":"run_tests", "arguments":{"code":"<含真实 Python 的字符串字面量>"}}`,
排除 schema 回显和示意性伪代码。唯一"不合规"之处是没包在 `<tool_call>` 标签里。

### 5.2 一个必须做的对照:离线重解析

有人会说"你的抽取器只是比 hermes 宽松而已"。为此把**同一批字节**用四种规则重新解析:

| 臂 | 服务端 | hermes 重放 | `<tools>` 重放 | 裸 JSON | tight |
|---|---|---|---|---|---|
| Qwen-1.5B | 0 | 0 | 0 | 0 | 0 |
| Qwen-3B | 0 | 0 | 0 | 5 | 4 |
| Qwen-7B | 0 | 0 | 0 | 22 | 21 |
| Qwen-14B | 0 | 0 | 0 | 42 | 36 |
| Qwen-32B | 0 | 0 | 0 | 100 | 80 |

**hermes 列在每一档都是 0——模型从来不产出那个格式。裸 JSON 和 tight 列不是。**

### 5.3 阳性对照:0% 不是管线坏了

在**同一个活跃服务**上,同模型、同 tools、同 prompt,只改 `tool_choice`:

```
tool_choice = auto      -> finish_reason = stop        tool_calls = 0
  content: "好的，下面是一个实现 count_distinct 的示例代码：```python..."

tool_choice = required  -> finish_reason = tool_calls  tool_calls = 1
  name      = run_tests
  arguments = {"code": "def count_distinct(nums):\n    return len(set(nums))"}
```

`required` 下 hermes 解析完全正常。

> **但这个对照的证明力有边界:** `required` 走的是**受约束解码**,强制输出符合格式。
> 所以它只证明"管线可用",**不证明"模型自发会用 `<tool_call>` 标签"**。
> 论文里这两句是分开写的——早期版本写成"因此 auto 下的 0 是模型行为,不是配置故障",
> 修订时降级为"这证明管线能接受合规调用,但不足以把 auto 下的 0 完全定位在模型"。

### 5.4 措辞上必须小心的地方

早期写法是"**模型越强,被吞掉的能力越多**"。这是**过度泛化**,修订时改成:

> **在 Qwen2.5-Coder 家族内,更大的 checkpoint 在同一错配接口下有单调更大的绝对低估。**

原因:这只是一个家族的一条规模梯子,一个任务,一个错配接口。而且
**参数量不等于能力**。审稿人一定会挑这条。

## 第 6 章 · 闭环:换对适配器能拿回多少

前面证明了"接口吞掉了东西",接下来要证明"换对了就能拿回来"。

社区为 Qwen2.5-Coder 提供了 `<tools>` 标签方案(vLLM issue #32926 / hanXen),
该 issue 已被 close as not planned(标签 stale)——**这个陷阱至今仍然生效**。

Qwen2.5-Coder-7B,同 100 题,`tool_choice: auto` 全程固定,只换适配器:

| 臂 | 解析出 | 平均轮数 | ≥2 轮 | 首轮通过 | 最终通过 | 多轮救回 |
|---|---|---|---|---|---|---|
| ReAct | 95 | 1.92 | 40 | 57 | **74** | 17 |
| FC + hermes | **0** | 0.96 | **0** | 53 | 53 | **0** |
| FC + 专用适配器 | **84** | 1.82 | **37** | 53 | **62** | **9** |

**机制层面全部恢复**:解析 0→84、进入第二轮 0→37、多轮救回 0→9。
**通过率只回收一部分**:53→62,p=0.093,未达显著。

### 6.1 一个漂亮的内部效度检验

**两个 FC 臂的首轮通过完全相同:53 vs 53。**

这不是巧合,而是**理论预测**:适配器只影响"第一轮之后发生什么",
不应该影响模型第一次写出的代码质量。数据正是如此。

> **教训九:好的实验设计里,应该有一个"如果我测的是我以为的东西,那么某个量必须不变"的检验。**
> 如果 53 vs 53 变成了 53 vs 61,就说明适配器还改了别的东西,整个归因就要重来。

### 6.2 归因边界

专用方案同时更换了 **parser、chat template、few-shot 示例**三者,
所以只能叫"**适配器组合**",不能把提升单独归因于 parser。
严格拆解需要模板 × parser 的 2×2 消融——**没做**,写进了 Limitations。

另外原模板的 few-shot 用的是 `get_weather`,与本实验唯一合法工具 `run_tests` 不符,
会诱导模型调用不存在的工具。已改写,原件保留为 `.orig`,两版 SHA256 都记录了。

### 6.3 适配器不是万能开关

同一个适配器在 7B 上恢复 84/100,**在 3B 上只有 1/100**——3B checkpoint 完全无视
`<tools>` few-shot(100 题里零个 `<tools>` 标签,99 条直接给代码),
但任务通过率还是差不多(最终 53)。

**适配器有效性在规模上非单调。** 再次印证"逐 checkpoint"这个结论。

## 第 7 章 · 训练侧:把同一机制测进 RL 的 rollout 里

前六章都在评测层。这一章要证明:**同样的错配会污染 RL 训练信号。**

### 7.1 实验

同模型、同数据、同超参、同 seed,**两侧 prompt 强度对齐**
(FC 用 mandatory 版:"**你必须先调用 run_tests 工具验证你的代码**,不要直接给出答案"):

| 臂 | 步数 | `num_turns/mean` | 工具耗时 | 每 rollout 工具调用 |
|---|---|---|---|---|
| FC(tool_agent + hermes) | 10 | **2.000** 恒定 | **0.00 s** | **0.000** |
| ReAct(react_agent) | 3 | 5.883(5.34→6.35) | 12.21 s | **2.052** |

### 7.2 计数是怎么做的(这段值得学)

verl 0.9.0 的 step 指标里**没有** tool_calls 次数。只有
`timing_s/agent_loop/tool_calls`——**那是耗时秒数,不是次数**。把它当次数是硬错误。

所以在 agent 侧两个调用点分别插桩:`CodeTool.execute`(FC 路径)与
`ReActAgentLoop._run_tests`(ReAct 路径),每次写一行带标签的日志。

> **关键:不能在 `sandbox.run_tests` 里计数。**
> 因为奖励函数评测最终代码也走那个函数,那样会把奖励评测混进工具调用数。
>
> 结果:FC 侧计数文件 **0 行**,ReAct 侧 **788 行**且标签全部是 `react`,来源无污染。

三条互相独立的证据一致:`num_turns` 恒为最小值 2、工具耗时精确 0.00 秒、专用计数 0。

### 7.3 冷启动:为什么这比"少了点信号"严重得多

有效调用**从第 1 步起就是 0**,而奖励函数允许直接输出代码拿分
(该 FC 臂的 `critic/rewards/mean` 从 0.233 涨到 0.281,**确实在涨**)。

于是策略梯度里**不存在任何把策略推向工具调用的信号**:
工具路径的回报恒为零样本,直接作答路径持续获得正回报。

**强制性 prompt 加 GRPO 不足以跨过这个冷启动**:模型无法通过探索发现工具路径,
因为它的每一次尝试都在协议层被丢弃,**从未产生过一条带正回报的工具轨迹供强化**。

### 7.4 措辞的边界(审稿意见逼出来的降级)

早期写法:

> ~~It renders a policy branch **unreachable by gradient**.~~

这是**数学上的过度声称**。因为:

- 策略对其他 token 的更新会改变整体分布
- entropy / exploration 理论上可能进入 parser 兼容的输出
- **观测到零样本 ≠ 概率支撑为零**

改成:

> The tool-using branch receives **no direct on-policy gradient signal under the observed
> rollout distribution**, and is **effectively inaccessible to policy-gradient learning in
> this cold-start regime.**

> **教训十:"我观测到 0" 和 "它的概率是 0" 是两件事。**
> 论文里凡是从有限样本推到全称命题的地方,都要加"under the observed ..."这样的限定。

### 7.5 另一条必须限定的:零执行 ≠ 零尝试

测到的是 **parser 接受并执行的调用为 0**,**不是**"模型从未尝试"。
FC 训练臂没保存原始 rollout 文本,所以三种情况无法区分:

1. 模型直接输出代码(没尝试)
2. 模型输出了畸形 `<tool_call>`(尝试了但格式不合规)
3. 模型有调用意图,但被 parser 丢弃

用相同 mandatory prompt 在同一个 1.5B 上做探针复刻(n=100):
**0 条合格调用、54 条直接作答、46 条无法解析、66 条含 JSON 片段但无一写出 `"name":"run_tests"`**。

所以在 1.5B 这个规模上,"本来就没有格式完好的调用可供 censor"是最可能的读法。

**正确写法:** *FC produced 0 parser-accepted / executed tool calls despite mandatory
instructions and correctly injected tool schemas.*
**错误写法:** *The model never attempted to call tools.*

## 第 8 章 · 一个零结果,和为什么它反而让论文更强

### 8.1 想做但做不成的实验

理想的因果对照是:

```
broken-FC RL   vs   repaired-FC RL
（固定模型/数据/算法/超参/奖励/seed/prompt/tool schema，只改 parser）
```

**这个实验在本技术栈里构造不出来。** 三层实测:

1. `multi_turn.format=hermes` 选的是 **verl 自己的 ToolParser 注册表**,
   挂 vLLM 插件无效(verl 有一套独立于 vLLM 的 parser)
2. 自己写 verl 侧 parser 能捞回调用,但**没有一条是那个工具**——
   36/52 调的是题目函数,16/52 代码在别处;**名字归一化救不了,因为没有代码可归一**
3. 角色歧义的补救(受约束解码 / 强制 tool choice)**verl 0.9.0 的 vLLM rollout 路径不暴露**
   (它唯一的 `strict` key 属于 profiler)

于是论文里明确写:**"在现有 verl 0.9.0 vLLM rollout 配置下,不存在可执行的
repaired-FC 条件。"** 这是训练栈的属性,不是"FC 原则上不可修"的证明。

**因此 ReAct 是"阳性对照的交互通道",不是"parser 修复对照"**,
该比较同时改变了协议与接口。**主动声明,而不是让读者读成单变量干预。**

### 8.2 退而求其次:TRAIN-01B

既然测不了"修好接口能不能恢复",那就测"**有一个能用的工具通道,够不够**":

ReAct,75 步 GRPO,同模型、同数据、同超参、同 seed、同评测钩子。
**该 run 执行了 23,676 次工具调用。**

| step | turn-1 | final | **≥2 轮救回** | repair 通道 |
|---|---|---|---|---|
| 0 | 359 | 367 | 8 | 263 |
| 15 | 340 | 346 | **6** | 266 |
| 30 | 340 | 346 | **6** | 262 |
| 45 | 341 | 349 | **8** | 261 |
| 60 | 341 | 347 | **6** | 274 |

**救回:6, 6, 8, 6 —— 净变化零。**

对比三个历史 run(工具调用执行数为 **0**):
`[7,9,6,6,7,6,10,8,9,8,6]`、`[8,7,6,7,7,7,7,5,6,6,8]`、`[7,5,7,5,7,8,9,9,8,9]`。

**两个条件在这个指标上无法区分。工具反馈到底有没有到达,对它没有可测量的影响。**

### 8.3 这个零结果给了论文什么

它**不允许**我们说"修好接口就能解锁多轮能力"——我们测了这个说法最接近的版本,失败了。

它**允许**我们说那个更窄、也更成熟的结论:

> **接口决定了工具中介的轨迹是否存在;它们的缺席足以解释为什么没有多轮信号——
> 但它们的存在不足以在这个规模和预算下产生多轮学习。瓶颈不是单一的。**

> **教训十一:一个诚实的零结果,比一个勉强的正结果更能撑住论文。**
> 审稿人看到"我们测了自己想要的结论,它没成立,所以我们把 claim 收窄了",
> 对整篇论文的信任度是上升的。

### 8.4 顺带一个运维事故

step-75 的评测丢了:step 75 的 checkpoint 写盘需要 4.86 GB,磁盘只剩 4.6 GB,
训练跑完之后进程 abort。

0–60 的趋势足够平,缺的那个点不会改变读法,但论文里**写明了这次丢失**,
而不是留一个没有解释的缺口。

> **教训十二:长任务开跑前先算磁盘。** 这是本项目第三次栽在"配置日志 ≠ 生效配置 / 资源没预估"上。

## 第 9 章 · 人工验证:一个用被截断的仪器去测量截断的故事

### 9.1 为什么需要人工验证

第 5 章那条规模曲线(0→4→21→36→80)**完全依赖一个自动分类器**
(`analysis/intent.py` 里的正则判据)。如果分类器判得不准,整条曲线就没有意义。

所以要做**人工验证**:抽一批样本,让人独立判断,和分类器比一致率。

### 9.2 第一轮:98 条,κ = 0.713

抽样设计:**按分类器判断分层**(40 条判 tight、28 条 strong 但非 tight、30 条两者皆非),
故意超采样决策边界,这样假阳性和假阴性都能估计。固定种子,顺序打乱,标注者只看原文。

结果:一致率 86.7%,**Cohen's κ = 0.713**,12 个假阳性、1 个假阴性。

> **知识点:什么是 Cohen's κ?**
> 两个评判者一致率的指标,但**扣掉了"瞎猜也会一致"的部分**。
> 如果两人都倾向于判 Y,那即使随机也会有很高的原始一致率。κ 修正了这个。
> 一般 κ>0.8 算很好,0.6–0.8 算不错,<0.6 就有问题了。

### 9.3 第一轮的裁决:一个结构性错误

12 个假阳性看起来都有同一个原因:**工具调用出现在文档中段,在一个 ```python
代码块之后**(匹配位置 1209–2585,而输出中位长度约 2000)。标注者读到代码块,
判断"这是直接作答不是调用",就停了。

于是做了"裁决轮":把有争议的条目的**匹配片段**单独拿给标注者看。
13 条里 10 条被翻转。裁决后 κ 升到 **0.936**。

**这个 0.936 后来被查出是无效的。** 审计裁决程序:

```
第一轮与分类器不一致        13 条
送去裁决                    13 条
两者重合                    13 / 13   ← 裁决集完全等于分歧集
裁决后朝分类器移动          10
裁决后背离分类器             0
```

**只复核分歧、且分歧按"与分类器不符"定义时,一致率只可能升不可能降。**
κ 从 0.713 到 0.936 是**选择规则的算术后果**,不是独立的可靠性证据。

> **教训十三:裁决集的选择规则必须先定、且不能引用你要验证的那个对象。**
> 正确做法:复核**所有评判者之间的分歧**,不看分类器判什么。

而且后果不是措辞而是数值:tight 层精确率在第一轮标注下是 28/40 = **0.700**,
裁决后是 38/40 = **0.950**。于是 32B 的 80 修正后落在 **[56, 76]** —— 一个巨大的区间。

### 9.4 第二名独立标注者:真相大白

做了一个盲标包给第二个人:同一批 98 条、重新打乱(编号与第一包无关)、
不含分类器判断、不含第一人任何标注、细则逐字相同。

**做包的过程本身踩了两个坑:**

1. 第一版从 `annotation_pack.md` 里用正则回捞原文。但**模型输出 98/98 都含
   ` ```python ` 围栏**,非贪婪正则在第一个内部围栏处就停了——**98 条里 71 条被截在任意位置**。
2. 我写的 `MAXCHARS=4000`"放宽上限"是**空操作**,因为第一包早已在 2400 处截过一次。

修法:从**原始轨迹 JSONL** 取全文,外层围栏换成 8 个 `~`(并校验不与正文冲突)。
逐字比对:98/98 与原始数据完全一致。

**第二名标注者的结果:**

| Cohen's κ (95% CI) | 全部 97 条 | **同字节 62 条** |
|---|---|---|
| A1 vs A2(inter-annotator) | 0.736 | **0.967** [0.897, 1.000] |
| A2 vs 分类器 | 0.936 | 0.967 |
| A1 vs 分类器 | 0.712 | 0.934 |

**12 条 A1–A2 分歧里,11 条是原文超过 2400 字符的条目**——而第一包正是截在 2400。
那 11 条 A1 全判 N、A2 全判 Y:**A1 说"没有调用",是因为调用被剪掉了。**

**κ = 0.713 那个"低可靠性"从头到尾是标注包截断造出来的。**

> 一个会截断的仪器挡在证据和观察者之间,出来的结论是"模型没有调用工具"——

## 第 11 章 · 贯穿全程的元教训

按重要性排:

1. **声称修好而未验证生效,比不修更危险。** 它同时污染数据和对数据的信任。
2. **排除了 N 个替代解释 ≠ 找到了真原因。** 单变量对照只能否定,不能肯定。
3. **不要用 `except: pass` 抹平不同的失败原因。** 出错时至少记下原始输入。
4. **警告没有强制力。** 要让错误必须被处理,就得非零退出码或异常。
5. **公平不等于相同的参数值。** 两个协议 token 效率不同,同样的上限就是不公平。
6. **每条数据都要带 provenance 落盘。** 而且 provenance 记的必须是**实际生效的值**。
7. **好的实验设计里要有"如果我测的是我以为的东西,某个量必须不变"的检验。**
   (FC 两臂首轮 53 vs 53 就是这样一个检验。)
8. **观测到 0 ≠ 概率为 0。** 从有限样本推全称命题要加限定。
9. **p > 0.05 ≠ 没有效应。** 报 CI 和效应量。
10. **裁决/复核的选择规则必须先定,且不能引用你要验证的那个对象。**
11. **诚实的零结果比勉强的正结果更能撑住论文。**
12. **当方法论出错的方式恰好是论文批评的那个机制时,把它写出来,别清理掉。**
13. **自动转换必须核对产物,不能只核对源文件。**
14. **长任务开跑前先算磁盘。**
15. **有些坑要认下来写进 Limitations,而不是立刻修**(修了会切断历史可比性)。
16. **阴性臂需要救援臂才有意义。** 一个 0 可能是"被 censoring 了",也可能是
    "它根本没试过"。Granite 在自己的 parser 下**也是 0**,这条救援臂才让我们
    敢判它"无信息量"而不是"确证"。没有它,那个 0 会被当成又一个案例写进论文。
17. **让自己有利的错误最危险。** 全档案首轮数第一版报 7205,去重后是 4254——
    错的方向恰好让数字更唬人。这类错误不会有人来纠正你。
18. **能拆成 2×2 就别只跑单臂。** "换 parser 有效"和"换模板有效"听起来是两个
    发现,2×2 才说出真相:**两个主效应精确为零,全部效应在交互项**。
    它把论点从"某个组件坏了"改成了"没有组件坏,是契约不匹配"——这是完全不同的论文。
19. **诊断也会错,而且会错很久。** "P3 卡在 verl 不暴露 guided decoding"这句话
    在复盘里躺了很多天,直到探针推翻它。**它和本文自己的论点是矛盾的**
    (本文主张接受模型发出的东西,guided decoding 是强迫模型)——
    自相矛盾就是诊断出错的信号,应该早点警觉。
20. **能实测就别估算。** 页数估了很多轮,装上 TeX Live 才发现估算低估 11%;
    "去掉表再编译"这个实测直接推翻了"往附录搬表能省很多"的策略。
    同类:换 ICLR 排版只省 1 页——这个我本来打算靠推理排除,幸好跑了一次。
21. **空的输出也是输出,要追。** 自评时有两行"删除: ……"内容为空,
    我看到了没查。那正是被我损坏的结论文件——**重复四遍,而且编译不报错**。
22. **对方指出的问题和对方给的修法要分开评估。** Codex 指出代理日志没有
    per-task 归属,建议修日志。修法不对(归属本来该来自 τ-bench 自己的 results
    JSON),但他指出的相邻风险是真的(未配对题怎么办),那条被采纳了。

## 第 12 章 · 第二轮外部验证（2026-09-01 → 09-03）

上一轮修订把评分从 4 推到 7,卡在 7 的理由只有一条:**所有证据都是自建 harness
测出来的**。这一章是为了拆掉那条。

### 12.1 BFCL v4:在别人的尺子上重测

把同一个漏斗搬到 Berkeley Function-Calling Leaderboard v4 上——**官方数据、
官方多轮执行器、官方评分器**,Gorilla 仓库钉在 commit
`6ea57973c7a6097fd7c5915698c54c17c5b1b6c8`。权重、题目、解码、种子、执行器、
评分器全部固定,**只换服务端适配器配置**。

结果:BFCL 自己的评分器给出 **0.00** 或 **0.96 / 0.19**
（`simple_python` / `multi_turn_base`）。

**这里有一个必须说清的偏离。** BFCL 给本地 Qwen 模型自带的 handler 是 POST 到
`/v1/completions`,然后**在 benchmark 进程内部**用正则抽 `<tool_call>` 块。
走那条路径**服务端 parser 根本不会被调用**,我们要研究的量压根不会出现。
所以我们改走 BFCL 自己的 OpenAI handler + `/v1/chat/completions`,只加两样:
显式 `tool_choice: auto`,以及把每个 HTTP 请求和 BFCL case id 连起来的 trace header。
数据加载、工具执行、评分全是 BFCL 的代码,`bfcl_eval` 的文件逐字节不动——
注册是在 import 时**在内存里**做的。

> **踩过的坑**:第一版 `register_qwen_coder.py` 用的是 `QwenFCHandler`,
> 它继承 `OSSHandler`——**那条路径同样绕开服务端 parser**。等于精心做了一个
> 测不到目标量的实验。后来改成基于 `P1OpenAIHandler`,并且把之前直接改
> `bfcl_eval/constants/model_config.py` 的磁盘补丁**撤回**、与 `.p1-orig` 逐字节比对确认还原。

### 12.2 2×2:全文最凝练的一张表

只换 parser 或只换模板都不够——但**到底是谁的功劳**,单臂对比答不了。
所以在同样 200 题、同样种子上跑了 template × parser 的 2×2:

| | documented template | dedicated template |
|---|---|---|
| `hermes` parser | 0/200 | **0/200** |
| dedicated parser | **0/200** | 196/200 |

**两个主效应精确为零,全部效应位于交互项。**

这张表的价值在于它**改变了论文的论点形状**。原来的说法是"parser 错配导致
调用被丢弃",听起来像"某个组件坏了"。2×2 说的是:**没有任何一个组件是坏的**。
换文档模板,模型把裸调用写进 ```json 围栏;换专用模板,它把**逐字节相同的载荷**
写进 `<tools>` 标签。两个 parser 各自都在正确地处理自己被定义去接受的包装层。
**一个已发表的基准分数是 0.00 还是 0.96,取决于这两边说的是不是同一种话。**

修一边,收益**恰好为零**。

### 12.3 τ-bench:交互式、有状态、有模拟用户

BFCL 是把一条轨迹和最终状态比对。τ-bench 多了一个模拟用户和一个有状态环境——
**一次被吞掉的调用,代价不是一个动作,是后面整段对话。**

115 道 retail 题,两臂全部配对,一道没丢:

| | documented | repaired |
|---|---|---|
| assistant 轮次 | 1389 | 1971 |
| 服务端解析出调用 | **0** | **636** |
| 发出但未被解析 | **789** | 6 |
| 进入过工具循环的题 | **0** | **103** |
| 解出的题 | 7 | 10 |

**任务成功差没有主张。** 3 个不一致对全在 repaired 方向,exact McNemar
**p = 0.25**,远不显著。能主张的只有机制:0 vs 636、0 vs 103。

两条必须和数字写在同一段(不能塞脚注)的限定:用户模拟器是本地
Llama-3.1-8B 而不是原 harness 的 gpt-4o,**绝对分不可与排行榜比**;
两臂对话长度天然不同,所以**所有量都按题算,不按请求算**。

> **这里有一个方法论上的分歧值得记。** Codex 提出代理日志的 `case_id`、
> `request_index` 都是空值,只能靠串行顺序关联,不够严谨,建议先修好逐题关联。
> 我不同意那个修法——**逐题归属本来就该来自 τ-bench 自己的 results JSON,
> 不是来自代理日志**。但他指出的相邻风险是真的:未配对的题怎么处理。
> 所以分析器改成显式报告配对数并丢弃未配对项(这次是 115/115,全配对)。

### 12.4 反事实梯子:同样的规模,匹配的接口

规模曲线有一个能精确说出来的混淆:服务端那列恒为零,所以增长**全部来自
发出列**——而大模型本来就更会写规整 JSON,跟工具调用没关系。

干净的检验是:在一个**包装层匹配**的梯子上重跑。如果 undercount 是规模的性质,
它在那里也该涨;如果是错配的性质,它压根不该出现。

Qwen3 提供了这样一个梯子。**预测("每个尺寸 parsed > 0")在跑之前提交进了仓库**
（`p4/PREREGISTRATION.md`）。结果:silent fraction 是 **1, 1, 2, 0**,
对着错配梯子的 0 → 4 → 21 → 36 → 80。

结论句的措辞收了一格,这一格很重要:

> 排除了"能力增长是**充分**原因";**没有**隔离出包装层,因为这个梯子
> 同时换了家族和包装层。

两条不埋起来的限定:parsed 列**不单调**(86, 44, 70, 97),所以这个梯子
说明的是**存在性,不是趋势**;Qwen3 是在 `enable_thinking=false` 下跑的,
因为开着 thinking 模型会把整个 token 预算花在 `<think>` 块里、还没发出调用就被截断——
这是与包装层无关的混淆,**作为协议偏离在跑之前就记录了**。

### 12.5 一个阴性结果,以及救援臂为什么必须做

想要第二个**表现出同样 undercount** 的家族,没拿到。事前普查九个家族的 chat
template:六个压根不注入 OpenAI 式 tools;剩下三个里,Granite-3.1-8B 在这个任务上
**根本不尝试调用工具**。

关键在于:我们既在 `hermes` 下跑了它,也在**它自己的 `granite` parser** 下跑了,
两边都是 0。**正是这条救援臂让我们能判定这个臂"无信息量"而不是"确证"。**
没有它,一个 0 会被误读成又一个 censoring 案例。

这条纪律是外部审稿逼出来的——我原本的预注册里没有救援臂。

### 12.6 失败层分解:论点从"parser 有 bug"变成"契约不匹配"

`analysis/failure_layer.py` 逐行复刻 vLLM 0.27.1 的 hermes 抽取器,在存档的
每一个首轮上重放,把每条丢失定位到具体的层:没有 `<tool_call>` 包装层 /
包装层在但 JSON 载荷坏 / 载荷合法只因 `json.loads` 不容忍尾随文本被拒 /
**真正的 parser 丢失**(重放成功而服务端失败)。

**全档案 4254 个去重首轮里,真正的 parser 丢失是 0 例。**

> **这个数字本身也踩了一次坑。** 第一版报的是 7205,后来发现档案里有 64 个
> 逐字节相同的镜像文件被重复计数。按内容 hash 去重后是 4254。
> 那个错误的方向**对我们有利**(数字更大更唬人),这类错误最危险。

这个 0 把论文的措辞逼着改了:**"censoring"从此指"尝试从未以 parser 被定义
去接受的形式抵达 parser",不是"parser 丢弃了合法调用"**。每个 parser 都在
严格按规范工作。坏掉的是三方之间的**契约**:checkpoint 被训练去发出什么、
chat template 告诉它发出什么、parser 被定义去接受什么——三者是各自独立配置的。

### 12.7 7B rollout 探针:把机制测进训练循环内部

1.5B 那个零是**过度决定**的——那个 checkpoint 在训练提示词下 0/52 的输出点名
`run_tests`,根本没有合规调用可供 censoring。所以它证明不了 RL 那部分的主张。

于是把探针塞进 **verl 自己的 AgentLoop**,在 7B 上、文档推荐配置下跑一个 rollout batch:

| | 计数 |
|---|---|
| 裸 JSON `run_tests` 调用,合法且完整 | **45** |
| 点名 `run_tests` 但载荷坏 | 12 |
| 没有尝试调用 | 58 |
| **被 verl 的 hermes parser 接受** | **0** |
| **工具执行** | **0** |
| **返回的 observation** | **0** |

**115 次生成里 45 次带着一个只要包上包装层就会执行的调用,没有一次抵达环境。**

这补上了 RL 主张最需要的那一环:在会发出合规调用的 checkpoint 上,
训练循环里工具轨迹的缺席**归因于接口,不归因于策略**。

**工程细节值得记**:verl 的 TaskRunner 是独立 Ray actor 进程,钩子必须走
`sitecustomize.py` + `builtins.__import__`,直接 import 装不上。而且钩子要拆成
`install()`(parser)和 `install_agentloop()`(`_call_tool`)两段,因为
`tool_parser` 导入完成时 `tool_agent_loop` 只是部分初始化。
脚本是自证式的:**任何一个钩子触发次数为 0 就写 `P3_INVALID`**——
这条救过一次,早期版本钩子没装上但脚本"成功"退出了。

**诚实记一笔**:这个 run 在 rollout 之后的 actor 更新阶段 **CUDA OOM**,
没有完成任何一个梯度步。rollout 观测全部产生于 OOM 之前,不受影响——
但这句得写进论文,不能省。

### 12.8 纠正一个我自己下错的诊断

复盘里原本写着 P3 卡在"verl 不暴露 guided decoding"。**这个诊断和本文自己的
论点是矛盾的,而且被 12.7 的探针推翻了。**

guided decoding 是**强迫模型输出某种格式**。但本文全篇主张的修法是相反的——
**让解析器接受模型已经在发的东西**(2×2 就是证据)。所以 repaired-FC 不需要
guided decoding,它需要的是往 verl 自己的 registry 里注册一个接受裸 JSON 的
ToolParser,而 12.7 已经证明代码能装进那套机制并截获每一次生成。

**真正挡路的是规模**:1.5B 上修好 parser 也没东西可接受(0/52 点名工具),
会发出合规调用的是 7B,而 7B 全参 RL 在单张 80 GB 上 OOM。
所以 P3 是**一个 7B + LoRA 的实验,不是换 rollout backend 的工程项目**。

### 12.9 指引住在错误的地方

普查九个家族的 HuggingFace model card,找任何提到 `--tool-call-parser` 的地方。
八张能访问的卡里,**没有一张提到它**,而其中六张推荐用 vLLM 部署。

发布方告诉你用哪个 server,server 问你用哪个 parser,**两边都不把配对当成
自己的责任**。这不代表错配在生产里很常见——我们查的是文档不是部署,而且
vLLM 为四十来个家族提供了专用 parser,照**它的**表配一般是对的。
能主张的更窄:**唯一一个能静默清零一次能力测量的配置项,在使用现场两边都没有文档。**

## 第 14 章 · 你需要补的知识(按优先级)

### 第一优先:直接决定你能不能自己 debug 这条链路

| 主题 | 为什么 | 建议材料 |
|---|---|---|
| **OpenAI Chat Completions API 的 tool calling 规范** | `tools` / `tool_choice` / `tool_calls` / `tool_call_id` 各自是什么,谁生成谁消费 | OpenAI 官方 function calling 文档 |
| **vLLM 的 tool calling 文档** | `--enable-auto-tool-choice`、`--tool-call-parser`、`--chat-template`、`strict: true` | docs.vllm.ai/features/tool_calling |
| **Jinja chat template** | 模型仓库里的 `tokenizer_config.json` 怎么把 messages+tools 渲染成一个字符串 | HF 的 chat templating 文档 |
| **受约束解码(constrained decoding)** | `tool_choice=required` 为什么一定能成功,`auto` 为什么不能 | Outlines 论文(Willard & Louf 2023) |

**动手建议:** 起一个 vLLM,故意漏掉 `--tool-call-parser`,发一个带 `tools` 的请求,
**亲眼看一次 HTTP 200 + `tool_calls: []`**。这一次比读十篇文档管用。

### 第二优先:读懂论文的实验设计

| 主题 | 为什么 |
|---|---|
| **McNemar 检验** | 全文所有比较都用它。理解为什么配对检验只看 b 和 c |
| **Cohen's κ** | 人工验证的核心指标。理解它为什么要扣掉"瞎猜的一致" |
| **置信区间 vs p 值** | §5.5 那个 [-0.5, +17.4] 是全文统计上最重要的一处修订 |
| **post-treatment conditioning** | 为什么"只看两边都解析成功的题"不是干净的因果估计 |
| **多重比较** | 十余次检验未校正,哪些能过 Bonferroni |
