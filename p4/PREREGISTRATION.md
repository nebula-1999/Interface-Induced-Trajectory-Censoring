# 预注册：跨家族的机制预测（写于运行之前）

**本文件在任何跨家族实验开跑之前提交。** 它的全部价值就在这个时间顺序上——
事后挑出对的那条来讲故事是没有意义的。

## 缘起：原计划的「第二个家族的 scale ladder」做不成

复盘 §12.3 把 P2 列为「第二个家族的 scale ladder」，用来判定 §5.2 是 scaling
现象还是 Qwen-plus-hermes 事实。零算力普查九个候选家族的 `chat_template` 之后，
结论是**候选池根本支撑不起一条梯子**：

| 家族 | 注入 tools | 信封 |
|---|---|---|
| Qwen3 | 是 | `<tool_call>` |
| Granite 3.1 | 是 | `<\|tool_call\|>` |
| GLM-4 | 是 | 无（中文 markdown 列表） |
| Phi-4 / InternLM2.5 / Yi-1.5 / StarCoder2 / DeepSeek-Coder-V2 / OLMo-2 | **否** | — |

**九个里六个的 chat template 压根不注入 tools**，与分类学里 DeepSeek 那一层同类，
不可能表现出 censoring；剩下三个各自只有一两个尺寸，凑不出 21× 那样的梯子。

这个"没有合格候选"本身是结果：它说明**接口错配不是罕见事故，而是常态**——
真正稀少的是"模板与 parser 恰好同意"的组合。

## 因此改做更强的东西：双向预测

2026-09-02 的 BFCL 2×2 给出了机制——**决定包装层的是 chat template**
（documented 模板让 Qwen2.5-Coder 发 ```` ```json ````，dedicated 模板让它发
`<tools>`，载荷一字不差）。这使机制可以**预测**，而不只是解释。

判据：在 `--tool-call-parser hermes` 下服务，看模板产出的信封是否是
`<tool_call>`。

### 预测（提交时间早于运行）

| 臂 | 模板信封 | **预测** | 若被推翻意味着 |
|---|---|---|---|
| **Qwen3-8B** | `<tool_call>` | **不被 censor**：服务端解析率显著 > 0 | 机制不成立——同信封也解析不出，说明还有别的因素 |
| **Granite-3.1-8B** | `<\|tool_call\|>` | **被 censor**：服务端解析率 ≈ 0，而离线可见合法裸调用 | 信封不是决定因素 |
| **GLM-4-9B** | 无信封 | **被 censor**：同上 | 同上 |

三条臂共用 §5.2 的题集（`clean_ids.json[:100]`）、同 `temperature=0`、`seed=0`、
`fc-schema terse`、`tool_choice=auto`，与 50 条已有臂逐项对齐。

### 这个设计为什么比原来的「梯子」强

- **有阳性对照**（Qwen3）。只跑被预测为 censor 的家族，无法排除"我们的探针在任何
  非 Qwen2.5-Coder 家族上都报 0"。
- **双向可证伪**：任一条不符预期都推翻机制，而不是只补一个数据点。
- **三个互不相关的家族**（阿里 / IBM / 智谱），排除单一厂商的实现习惯。

### 已知局限（同样先写下来）

- 每个家族只有单一尺寸，**这不是 scale ladder**，不能用来支持或推翻 §5.2 的
  规模主张。原意义上的 P2 仍然开着，且按上表看在现有开源模型里可能无法完成。
- 判据只看模板文本，不看模型实际训练成什么样。模板与训练不一致的情况确实存在
  ——§5.1 里 Qwen2.5-Coder 继承 Instruct 模板正是一例，那也是预测可能失败的方式之一。
