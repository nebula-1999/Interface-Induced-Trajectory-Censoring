## 2. 开跑前必须先修脚本里的三处

我审过 `fixes/run_p0.sh`，它有今天已经害我失败两次的同一类问题：

### 2.1 裸 `python` 调用（3 处：第 13、25、37 行）

脚本靠第 9 行 `source /root/autodl-tmp/env.sh` 激活 venv 才有 `python`。
**但用 `setsid --fork` 脱离终端启动时，走的是另一套 PATH**，`env.sh` 里的
`source $VENV/bin/activate` 在非交互 shell 下不一定生效。今天 P1 死在
`python3: command not found`、P3 死在 `python: command not found`，各浪费一次启动。

**改法**：脚本开头显式钉死，并自检存在：

```bash
PY="${P0_PYTHON:-/root/code-venv/bin/python}"
[ -x "$PY" ] || { echo "★ 找不到解释器 $PY"; exit 1; }
```

然后把三处 `python` 换成 `"$PY"`。

### 2.2 BLAS 线程没钉死

`fixes/run_p0.sh` 里**没有** `OPENBLAS_NUM_THREADS`。这台 112 核，沙箱子进程
一 `import numpy` 就会因线程池缓冲区超掉 `RLIMIT_AS` 而报
`OpenBLAS error: Memory allocation still failed`，症状很像数据问题。加上：

```bash
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1
```

### 2.3 磁盘防线

见下一节。P0 本身产出很小，但**没有任何余量**。

## 3. 磁盘：只剩 3.9 GB，这是最可能毁掉整轮的东西

「4.86 GB required, 4.6 GB free」，进程在训练**已完成之后**中止，
step-75 的评测数据直接丢失——这件事写在论文 §5.8 的 caveat 里。

P0 不训练、不写 checkpoint，所以主要风险是 vLLM 的编译缓存和意外写入。


`deepseek-coder-1.3b`（5.1G）。**但它们是四家族结果的复现依赖，删了要重下**——
建议先不删，跑起来盯着 `df`，真不够再说。
